# 残る性能差の調査 — 2026-10-24

対象コミット: `1ba91b6`。製品コンパイラ、ランタイム、既存ベンチのソースは変更していない。
公式の比較値は [全16種・48条件](../results.md) を参照。この調査の値で公式表を置き換えない。

## 差が大きい種目

large 条件、各言語の最速測定値との比較。

| 種目 | R^ ms | C++ ms | Rust ms | 主な改善候補 |
|---|---:|---:|---:|---|
| blur | 4939.43 | 584.01 | 714.85 | ループの境界証明・検査の外出し、自動ベクトル化 |
| graph | 6732.20 | 2161.42 | 2183.24 | 連結辺から CSR へのデータ配置変更 |
| bintrees | 1441.40 | 856.58 | 678.31 | スカラー呼び出し規約、再帰の一時領域削減 |
| scene | 1727.81 | 975.82 | 905.10 | 別名解析、行列処理、変換・集約値の受け渡し（追加調査が必要） |
| lru | 7507.82 | 4443.07 | 4817.90 | 内部リンケージと引数最適化、続いて範囲証明 |
| sexp | 3799.99 | 2511.50 | 2320.62 | 所有文字列コピーの差、タグ検査、再帰の受け渡し |

`graph` の同じ連結インデックス表現に絞ると C++ clang-cl は 6615.95 ms、
Rust arena は 7089.08 ms。R^ の 6732.20 ms と近い。
最速 CSR 版との約3倍の差を、コンパイラだけの差と解釈するべきではない。
CSR は次数集計→累積和→連続辺配置で構築し、BFS のポインタ追跡を避ける。
現在の R^ の固定サイズ配列要素・伸長配列・整数操作で試作でき、言語機能の追加は必須ではない。

## 診断用の切り分け

medium 入力。2回のウォームアップ後、3回の最小のプロセス全体時間。
実行順を交互に反転し、毎回チェックサムと実行ファイルの SHA-256 を照合した。
100回と30回、合計130回が一致。実行時間は別セッション間で直接比較しない。

`internal` は R^ の生成関数だけを LLVM の内部リンケージにする。
`unchecked` は一時コピーの LLVM IR で添字検査の分岐だけを無条件成功に変更する。
**unchecked は安全でない診断実験であり、実装案でも提供機能でもない。**
容量・除算・タグなど他の検査は維持する。高速化の余地を切り分ける目的に限る。

| 種目 | 現行 ms | internal ms | unchecked ms | 両方 ms |
|---|---:|---:|---:|---:|
| blur | 327.14 | 302.34 | 42.83 | 45.60 |
| lru | 1514.29 | 1034.58 | 1574.13 | 761.53 |
| bintrees | 324.29 | 291.53 | 300.98 | 299.70 |
| scene | 281.84 | 273.76 | 279.47 | 259.69 |
| calc | 314.94 | 307.88 | 315.06 | 295.85 |

`blur` は検査を外した場合に約7.6倍速くなった。
最適化後の現行相当の blur 本体には、9読み込み＋1書き込みの添字検査が残る。
LLVM の [診断](blur_internal.remarks.txt) は複数の早期終了と配列範囲の不明を挙げ、
[検査除去時](blur_unchecked.remarks.txt) には幅16の自動ベクトル化を報告した。
単に比較命令10個のコストではなく、ループ最適化への影響が大きい。

`lru` は internal だけで約1.46倍、検査除去との組合せで約1.99倍。
単独の検査除去はこのセッションでは速くならず、効果は加算的ではない。
現状はプログラム内だけで呼ぶ関数も外部可視で、LLVM による引数の変更・特殊化を制限する。
所有値の構築先を変えず、外部公開されない関数に内部リンケージを付けるのが小さい改善候補。
将来のエクスポート関数は区別する必要がある。

一方 scene と calc は添字検査除去の効果が小さい。
これらの残る差まで境界検査で説明する根拠は得られなかった。

## 対象を絞った追加実験

| 種目 | 変形 | 現行 ms | 実験 ms | 現行 / 実験 |
|---|---|---:|---:|---:|
| bintrees | scalar_abi | 301.11 | 193.28 | 1.56x |
| calc | inline_tags | 314.50 | 299.94 | 1.05x |
| sexp | inline_tags | 1245.96 | 1157.98 | 1.08x |

`scalar_abi` は bintrees のスカラー・参照引数を LLVM の値として直接渡し、
整数結果を `ret i32/i64` で返す。内部リンケージも同時に適用しているため、
この1.56倍を ABI 単独の効果とはしない。添字・容量検査は維持した。

現行は整数引数まで `ptr %argN`、結果も `ptr %out` で渡す。
最適化後も make/check の再帰のたびに引数と戻り値用の alloca/load/store が残っていた。
まずスカラー・参照を直接渡し、大きい集約値と所有値は構築先渡しを維持する方針が有力。
再帰の強連結成分や所有スタックのルールを変える必要はない。

`inline_tags` は `.get` のタグ一致比較を LLVM IR に置き、失敗時だけ従来の
`rh_union_tag` に渡す。検査を外さず、正常時のランタイム呼び出しを除く。
最適化後でも calc に `rh_union_tag(0,0,...)` のような成功が確定した呼び出しが残っていた。
改善はこの条件で約5〜8%で、候補ではあるが blur／呼び出し規約ほど大きくない。

## 推奨順序

1. **内部リンケージ＋スカラー引数・結果の直接渡し。** 小さい変更から始められ、lru／再帰に実測根拠がある。
2. **範囲証明とループの高速経路。** blur が最大の改善余地。行単位・ループ単位で全アクセスの範囲を証明する。
   証明できない場合は既存の検査付き経路を使う。符号付き演算の折り返し、空配列、境界値、エラーまでの副作用を維持する。
3. **graph の CSR 版を追加。** 既存連結版も残し、同じ配置同士と最速配置の両方を比較する。
4. **タグ検査のインライン化。** 比較的局所的な改善。追加の型・所有機能を必要としない。
5. **scene の追加切り分け。** 行列更新、float→整数検査、集約値コピー、別名解析の寄与を別々に測る。

別名情報は、所有元の非重複を証明した箇所に限って付ける。
R^ は同じ配列を複数の参照引数に渡せるため、借用引数すべてに noalias を付ける案は使えない。
blur のベクトル化にも必要なら所有元の証明、または実行時の重なり判定を利用する。

bintrees の領域・コミット済みページ再利用は前回で実装済みであり、今回はそれを変えていない。
その先にも、再帰の受け渡しやノードへのアクセスのコストが残っている。

## 再現用資料

開発シェルで次を実行する（current の比較バイナリと保持した .ll が必要）。

```powershell
python bench/investigation/codegen.py
python bench/investigation/targeted.py
```

[切り分けの生データ](codegen.json)、[追加実験の生データ](targeted.json) に
反復ごとの値、チェックサム、実行ファイルハッシュ、ビルドコマンド、実行したスクリプトを保持した。
これはプロファイラの時間占有率測定ではなく、生成コード確認と限定した変形の比較である。
