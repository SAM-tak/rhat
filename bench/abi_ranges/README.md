# 内部呼び出しとループの範囲証明

今回の製品コンパイラによる [7種×3サイズの交互測定](results.md)。
旧版は `1ba91b6` の生成コード、新版は内部リンケージ・スカラーの直接渡し・
検査付きループの高速経路を含む。元のベンチソースと入力サイズを変更していない。

| large 条件 | 旧版 ms | 新版 ms | 旧版 / 新版 |
|---|---:|---:|---:|
| blur | 4897.97 | 492.07 | 9.95x |
| lru | 7566.02 | 3892.31 | 1.94x |
| bintrees | 1430.20 | 819.50 | 1.75x |
| scene | 1731.28 | 1493.59 | 1.16x |
| calc | 1238.68 | 1081.97 | 1.14x |
| push | 354.37 | 327.29 | 1.08x |

C++／Rust の時間・比率も表に残している。ただし、その列は前回の全体測定の参照値であり、
今回取り直した値ではない。今回の同一セッション比較は R^ の旧版と新版。
全16種・48条件の [直前の完全な比較表](../results.md) も保持している。

`sum` は改善したとは判断しない。最初の3回の最小値では large が 691.50 → 731.26 ms。
ばらつきを確認するため、ウォームアップ2回＋本測定7回を交互実行したところ、
最小値は 684.00 → 695.86 ms、中央値は 696.09 → 709.10 ms で、約2%の低下が残った。
[追加測定](sum_repeat.json) も保存している。すべての種目が速くなったという主張はしない。

## 実装の範囲

- R^ 内の関数は内部リンケージ。整数・bool・浮動小数点・参照は LLVM の値として渡す。
  集約値と所有結果は従来の構築先渡しを維持し、寿命・スタック配置の検査を変えていない。
- 単純な `i64^` の単位増加ループで、全反復の添字範囲を入口で検証する。
  加減乗算の途中も含めた折り返しを128ビットの区間評価で検出する。
- 証明した経路では上限と配列データポインタを保存して使う。
  保証できなければ元の検査付き経路を実行し、エラー位置とその前の副作用を維持する。
- 呼び出し・伸縮・複雑な制御フローがあるループは対象外。
  借用引数すべてに noalias を付けることはせず、重なる配列・スライスも許可する。

`blur` の [LLVM 診断](blur_vectorization.txt) で幅16の自動ベクトル化を確認した。
明示的な SIMD 命令や、利用者が検査を無効にする指定は追加していない。

## 検証

468件の統合テスト（実行テストは `-O0`／`-O2`）が通過。
スカラー全型の引数・戻り値、再帰、所有結果、空配列、巨大な境界、演算の折り返し、
同じ配列への複数の参照、重なるスライス、途中での除算エラーを確認した。
対象ループでは高速経路のある版と、ガードを強制的に失敗させた検査付き経路の出力・診断も照合。
40通りの動的な係数・開始位置の組合せも含む。

性能比較は42本の実行ファイル・210回、追加の sum は18回。
各実行でチェックサムと SHA-256 を照合し、ソース・LLVM IR・コンパイラ・ランタイムも識別している。
Release／Debug ビルド、厳密な C の警告検査も通過した。

再測定には、開発シェルで `python bench/abi_ranges/measure.py` を実行する。
旧版の比較バイナリと .ll を保持した `build/bench-array`／`build/bench-array-bintrees` が必要。
[生データ](results.json) にコマンド、反復値、測定スクリプト、参照値を保存している。
