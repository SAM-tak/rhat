# 言語サーバー（rhat lsp）

`rhat lsp` は C11 で実装した stdio 接続の Language Server Protocol サーバーです。
L^ の通信、JSON-RPC、URI、UTF-16 座標変換、スレッドの実装を移植し、
解析部分は R^ の構文解析・名前解決・型検査・寿命検査・データスタック検査へ接続しています。
L^ の VM、ホスト設定、LTON、可視化専用 RPC と DAP は組み込みません。

## 起動とインストール

言語サーバーは独立した実行ファイルではなく、`rhat` のサブコマンドです。

```powershell
cmake -S . -B build
cmake --build build --config Debug
.\build\Debug\rhat.exe lsp --stdio
```

エディターの LSP クライアントから、この実行ファイルを子プロセスとして起動してください。
標準入力・標準出力は Content-Length 付き JSON-RPC 専用です。
VS Code では言語クライアント拡張から接続する必要があります。
LSP クライアントそのものは、このリポジトリには含めません。

```powershell
cmake --install build --config Release --prefix C:/tools/rhat
C:/tools/rhat/bin/rhat.exe lsp --stdio
```

ビルドのたびに、`rhat` は `.rhat-ls/`（`RHAT_SERVER_DIR` で変更できます）にもコピーされます。
エディターにはこのコピーを起動させると、サーバーの実行中でもビルドできます。
コピーが使用中で更新できないときは、ビルドが警告を出すだけで失敗しません。サーバーを止めると次のビルドで更新されます。

インストール先の `share/rhat/stdlib` を優先し、開発時には同梱ソースの `stdlib` を使います。
`--stdlib DIR` で探索先を指定できます。`DIR/std/random.rh` が存在する配置を指定します。
外部の L^ チェックアウトや、ビルド時のネットワーク取得は不要です。

## 対応機能

- 構文・型・公開制御・参照寿命・所有領域について、コンパイラと同じ診断。
  波線はコンパイラが保持するソース上のトークン範囲を使い、識別子の前方検索で位置を補正しません。
  存在しないフィールドやメソッドはその名前を指します。
- `template^` 関数の具体化で見つかったエラーは、本体と、その具体化を要求した呼び出し位置の両方に報告します。
  同じ具体化を使う複数の呼び出しや、テンプレートを介した呼び出しの連鎖も追跡します。
  `relatedInformation` で本体と呼び出し元を関連づけ、別ファイルにも移動できます。
  CLI では本体のエラーに続けて、具体化の要求元を `note:` で表示します。
- ローカル変数、引数、フィールド、構造体型、関数・メソッドのホバーと定義移動。
  型を呼び出し側に任せた引数を持つ関数は、解析で得た具体化を交差として並べて表示します
  （`write : p^x:i32^; & p^x:string^;`）。具体化が一つなら `;` なしの単独署名です。
  呼ばれていない間は `?` のままです。
- 解析済みの参照検索、文書内ハイライト、文書シンボル、ワークスペースシンボル。
  文書シンボルは `DocumentSymbol.children` による階層で返し、型の下にメンバー、
  関数・メソッドの下に解析済みのローカル宣言を表示します。構文解析から宣言全体の範囲を取り、
  選択・移動用には名前トークンの範囲を別に保持します。ワークスペース検索は従来の平坦な一覧です。
  文書シンボルの要求中に保存通知や別文書の変更で解析状態が更新された場合は、
  最新の文書群で要求を再実行します。`ContentModified` を空の Outline として保持するクライアントでも
  表示が失われたままにならないようにし、明示的なキャンセルは引き続き受け付けます。
- 名前、組み込み型、言語構文、名前空間、構造体メンバ、配列メンバの補完。
- 継承と非公開メンバを考慮したメンバ補完。
- 関数・メソッドのシグネチャヘルプ。関数の別名では交差の各署名を表示。
  戻り値なしの署名は `->` 以降を省略し、`nil^` を返す署名の `-> nil^` と区別します。
  表記は `reseed : p^self^:std.random.Random, seed:i64^` のように、R^ の引数リストを使います。
- 引数型で選択したオーバーロードと、利用者定義演算子の定義移動。
- 解決済みの型、関数、引数、変数、フィールドなどの semantic tokens。
  型エイリアスの使用範囲は、解決先の型名ではなくソース上の綴りの長さで記録します。
  `let^` の値と `enum^` のリーフは、宣言・参照とも `variable.readonly` として定数の色付けを使います。
  インポートしたモジュールのパス各部と別名は、宣言・使用箇所とも `namespace` として色付けします。
  コメント・文字列・数値・キーワード・演算子は TextMate 文法に任せ、`^` の薄い配色も上書きしません。
- UTF-16 座標による差分編集と全文置換。日本語・補助平面文字・CRLF に対応。
- 未保存の文書と未保存の依存モジュールの解析。文書バージョンの逆行を拒否。
- `textDocument/formatting` による全文整形。CLI と共通のエンジンと EditorConfig を使い、未保存バッファの編集を返します（[整形](formatting.md)）。
- 保存・外部ファイル変更通知による再検査、診断の消去、リクエストのキャンセル。

`initialize` の `workspaceFolders`、または従来の `rootUri` をモジュール探索に使います。
追加の探索先は `initializationOptions` で指定します。

```json
{
  "modulePaths": ["C:/work/project/modules"]
}
```

パスは絶対パスで渡してください。標準モジュールは、コンパイラと同じく専用の標準ライブラリから探索します。
独立して開いた `module^` ファイルも、ライブラリの宣言として検査します。
そのため、公開定数を含むライブラリを編集するために、仮のエントリーファイルを作る必要はありません。

## コンパイラとの接続

フロントエンドに `tooling` オプションと、検査済みの名前解決記録を追加しています。
メンバは実際に選ばれたフィールド・メソッドへ、公称型は宣言元へ、ローカル名は選択された束縛へ結び付けます。
`&` 以降の名前を省いたオーバーロード枝は、宣言位置を `f^` / `p^` / `template^` の
キーワードの範囲に限定し、引数を関数名の色で覆いません。`externC^` / `externLLVM^` の
引数も署名から宣言として記録し、本体を持つ関数と同じ引数の色を使います。
同名の別モジュール・別スコープを、文字列の一致だけで同一視しません。
自動破棄・エラー表示・文字列補間で生成する内部呼び出しは、ソース上のメソッド参照として登録しません。
利用者定義演算子の呼び出しは、実際に書かれた演算子の位置に対応付けます。
型が決まっている箇所では、通常の型推論とナローイングの結果を表示します。
通常のコンパイルでは、これらの記録とソース保持を行いません。

まだ具体化されていない `template^` や型パラメータ付き定義の本体にも、
明示された型名、一意に決まる関数・静的メソッド、ローカル束縛の参照を記録します。
`thread_entry^` などの組み込み操作には、ホバー・補完・シグネチャヘルプ用の署名を用意し、
その戻り型が引数によらず決まる場合は、ローカル変数のホバーにも使います。
引数型が必要な部分は `?` または署名中の型パラメータとして残し、具体化を強制しません。
同名のローカル束縛による遮蔽を追跡し、検査済みの型情報がある場合はそちらを優先します。
組み込み操作にはソース上の宣言がないため、定義ジャンプ先は返しません。

`CompilerHooks` は検査用の割り当て境界と診断境界です。
検査中の確保を一回の解析単位で回収し、言語の診断は `setjmp` / `longjmp` の境界へ戻します。
CLI ではフックを設定しないため、従来どおり診断を表示して終了します。
LSP では最初のエラーで解析全体を打ち切らず、同じ編集状態の後続コードも検査します。
ディスクのソースを書き換えず、オーバーレイをモジュール探索と読み込みへ渡します。

復帰の方針は L^ と同じく、独立した誤りを報告し、先行エラーに由来する連鎖診断を
抑えるものです。壊れた字句は行末まで、構文は波括弧と次の文・メンバ・宣言を手掛かりに
読み飛ばします。閉じていないブロックコメントは後続コードとの境界がないため末尾まで扱います。
文の検査に失敗した場合はスコープ・束縛・ナローイング・エラー処理・途中の中間コードを
その文の前へ戻し、次の文を検査します。失敗した束縛や型・import に依存する検査は、
同じ原因を再報告せずに中断します。未知の型に仮の具体型を与えて検査を成功させません。
初期化式が壊れていても、解決済みの変数の型注釈はホバーに残します。束縛自体は失敗扱いを維持し、
その値を利用する検査によって派生診断を増やしません。

トップレベル変数の捕捉用に追加する隠し引数は、利用者が書いた未注釈引数と区別します。
エントリの検査に失敗し、捕捉の呼び出し形状が得られない場合は、その派生診断を抑えます。
利用者が書いた未注釈引数の独立した診断は残します。先行エラーがない未使用関数で捕捉型が
決まらない場合は、元の変数名と関数の宣言位置を示し、変数への型注釈または関数呼び出しを案内します。

型注釈は関数本体と別に解決するため、未使用関数も先行エラーに左右されず型名を色付けします。
一度の解析では重複を除いて最大100件の診断を返し、修正した版では診断を再計算します。
正常な箇所のホバー・定義ジャンプ・色付けは、その版で得た情報を使います。
型の構成や関数の署名自体が壊れている場合、その型に依存する本体の情報には限界があります。
復帰中の中間コードは実行用に使用しません。CLI の `check` / `build` は引き続き最初のエラーで終了します。

受信スレッドは編集・キュー・初期化・終了処理を担当し、検査は一つのワーカースレッドに限定しています。
待機中の再検査は合流し、古いバージョンの解析結果は公開しません。
同じ編集状態での問い合わせには解析済みのインデックスを再利用します。
文書を閉じると、その未保存バッファを外し、残る文書を再検査します。

位置情報を出力するときは、解析単位でソースの行開始位置・UTF-16の行番号・URIを
保持します。参照ごとにファイル先頭から走査したり、同じパスを再変換したりしません。
参照の重複除去には、宣言・使用位置・宣言フラグをキーにしたハッシュ集合を使います。
同じ使用箇所に異なる宣言が対応する場合と、具体化ごとの最初の解決結果を保持します。

semantic tokens は要求ごとに、その文書のバイト位置から解決済みの参照を引く表を作ります。
同じ位置の参照は従来の順序で選び、トークン末尾より隣接トークンの内部を優先します。
UTF-16座標も先頭から再計算せず、トークン順に進めます。作業用の表は応答時に解放します。

古い文書版への要求は解析前に `ContentModified` で応答します。文書を順に検査している途中で
編集が入った場合も、次の文書へ進む前にその解析を打ち切ります。最新の診断を、古い版の
補完や色分け要求のために何回も待たせないようにしています。

## 現時点の範囲

解析対象は開いている文書と、その静的な import 依存です。
参照検索とワークスペースシンボルも、この解析済みの範囲を対象にします。
未使用のテンプレートなど、コンパイラが本体を具体化していない部分の型情報は限定的です。
同じ構文位置に複数の具体化が対応する場合、ホバー・定義移動では最初に得た解決結果を使います。
構文エラーで構文木を作れない場合には、取得できた宣言までを表示します。
メンバ補完では編集中の `receiver.` を補修して検査する経路も用意しています。
診断は CLI と同じく、一つの検査対象で最初のエラーを表示します。

名前変更・コードアクション・範囲整形・入力時整形は、未対応の機能として capability を通知しません。
特に、具体化していない本体まで完全に追えていない状態で、一部の参照だけを書き換える rename は提供しません。

## デバッグについて

R^ 専用の DAP サーバーは作りません。
ネイティブ実行ファイルには、GDB・LLDB・Windows デバッガと、それらの既存のアダプターを利用できます。
VS Code のデバッガ UI 自体は DAP を使うため、「DAP を使わない」ではなく、
「R^ 独自の DAP サーバーを実装しない」という分担です。

ただし、現在の LLVM IR には R^ のソース位置・変数型を表すデバッグ情報を出力していません。
R^ ソース上のブレークポイントや変数表示を実現するには、別途 LLVM のデバッグ情報を生成する必要があります。
LSP の位置・型情報を追加しただけでは、実行ファイルにその情報は入りません。

## 検証

`tests/lsp.py` は実際の `rhat lsp` と Content-Length 付き stdio メッセージを交換します。
未保存バッファ、依存変更、構文・意味エラーからの復帰、UTF-16、名前解決、補完、
公開制御、連続編集、初期化・終了を検証します。CTest の `lsp` として登録しています。
大きな参照一覧、UTF-16とCRLFの座標、連続入力中の古いsemantic tokens要求も含みます。
複数エラーの同時報告、依存先からの連鎖診断の抑制、文・メンバ・字句・import の復帰、
エラー後の未使用署名の色付けと後続コードのホバー・定義ジャンプも検証します。

実ファイルでの編集から情報更新までの時間は、次のコマンドで計測できます。

```powershell
python bench/lsp_latency.py --server build/Release/rhat.exe `
  --source ../rhat-gfx/samples/mini_doom.rh --module-path ../rhat-gfx `
  --open stdlib/std/math.rh --open ../rhat-gfx/gfx.rh --open ../rhat-gfx/audio.rh `
  --samples 20 --limit 1 --output build/lsp-latency-final.json
```

ソースをディスク上で変更せず、未保存の編集をLSPのstdioで送ります。エラーを入れて診断が
出ることを確認し、修正後は診断の消去・semantic tokens・新しい宣言のホバーまでを計測します。
元のソースが検査を通ることを前提とします。
20回の連続編集と色分け要求の後でも同じ確認を行い、いずれかの更新が1秒を超えると失敗します。
2026-11-01のWindows Releaseビルドでは、4文書を開いてエラーと修正を20回ずつ、
初回表示と連続入力後の修正も含む42件を計測し、情報更新までの最大時間は0.594秒でした。
同じ `mini_doom.rh` のsemantic tokens単独の処理は45.3秒から0.057秒に短縮し、
出力した5,065トークンは旧版と完全一致しました。
エラー復帰の導入後も、同じ4文書・42件の計測で最大0.419秒でした。こちらの計測では、
編集中の `mini_doom.rh` の `Self^` を `F2` に置き換えた検査用コピーを使用し、元ファイルは変更していません。

### 索引生成とファイルパス比較

Outline 用の構文範囲は、解析ごとにファイル別のバイト位置へ一度だけ変換します。
各シンボルの範囲検索では、そのファイルの変換済み範囲から最も狭いものを選びます。
全ファイルの範囲についてパス照合・座標変換を繰り返しません。
Windows では正規化不要なドライブ付き絶対パス同士は文字列比較で判定し、
相対パス・`.` / `..` を含むパス・UNC パス等には従来の正規化を使います。
未保存の依存先を別表記のパスから参照する動作も維持します。

2026-11-11 の Windows Release ビルドで `mini_minecraft.rh` を測定したところ、
変更前は構文解析・意味解析の約0.2秒に対し、索引生成だけで約2.6秒かかっていました。
同じ環境で末尾コメントの未保存編集を各3回行った、編集から診断通知までの中央値は次のとおりです。

| 開いている文書 | 変更前 | 変更後 |
| --- | ---: | ---: |
| `mini_minecraft.rh` のみ | 2.760秒 | 0.512秒 |
| 上記と `mini_doom.rh`、`gfx.rh` | 5.735秒 | 0.941秒 |

3文書を開いた既存ベンチマークでも、エラー・修正を各3回と20回の連続編集後について、
診断・semantic tokens・新しい宣言のホバーの更新を確認し、最大1.322秒でした。
ソースはディスク上で変更していません。時間は環境依存で、通常の機能テストに固定の時間上限は置きません。

移植元のライセンスは `lsp/LICENSE.lhat`、cJSON は `vendor/cjson/LICENSE` に保持しています。

## try^ の行き先

`try^` のホバーは、エラーの型ごとの行き先を表示します。定義へ移動すると、最初の行き先へ飛びます。

```text
try^: E.Bad | E.Other
E.Bad -> catch^ at 12:5
E.Other -> catch^ at 15:1
```

- `catch^` が受けるなら、その腕の行と桁。型付きの腕で受けきれない分は、外側の節へたどります。
- 受ける腕がなければ、関数の結果に合併されるので、`result of 'f' at 5:12` とその関数の位置。
- トップレベルで受ける腕がなければ、`out of the unit: the runtime reports it and exits`。

実行時の経路と同じく、生成時の `catch^` の並びから求めます。型を書かない引数の関数では、具体化ごとに行き先が異なることがあり、そのときは最初の具体化の結果を表示します。
