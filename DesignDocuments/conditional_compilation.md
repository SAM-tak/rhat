# 条件付きコンパイル（設計メモ・未実装）

R^ には OS やターゲットによってコードを切り替える仕組みがまだありません。
今は OS の違いを C のランタイム（`runtime/rhat_runtime.c` の `#if defined(_WIN32)` など）に押し込み、
R^ 側からは同じ署名の `rh_*` 関数として呼んでいます（例: `std.fs` の `rh_fs_open`、`std.random` の `rh_random_seed`）。
Goose も同じ方針で、言語には条件付きコンパイルがありません。

R^ のコードそのものに OS ごとの差分が増えてきたら（OS ごとの C ライブラリのバインディングなど）、言語で扱う必要が出ます。

## 他の言語

- **Rust**: 項目に付ける属性 `#[cfg(windows)]`、`#[cfg(target_os = "macos")]`。条件に合わない項目は名前解決の前に構文木から消える。
  条件は `all()`・`any()`・`not()` で組み、`feature = "..."` で利用者が選ぶ機能も表す。式の `cfg!(...)` は bool を返し、両分岐とも型検査される。
  標準ライブラリは `sys/windows`・`sys/unix` のようにモジュールごと切り替えている。
- **Zig**: `if (builtin.os.tag == .windows)` はコンパイル時に評価される普通の `if`。選ばれなかった分岐は解析しない。
- **Go**: ファイル単位。`x_windows.go` のような名前の接尾辞か、先頭の `//go:build linux` でファイルごと含める・外す。
- **Swift**: `#if os(Windows) ... #endif`。書ける条件は決まったものだけで、テキスト置換ではない。
- **Nim**: `when defined(windows):`。コンパイル時の `if`。

C のプリプロセッサ型（テキスト置換）は採らない。括弧の対応が崩れる、ツール（LSP）が片方の分岐しか見られない、といった問題が出るため。

## R^ での候補

1. **モジュールのファイルを分ける（Go 型）**: `import^ std.fs.os` を、ターゲットに応じて `fs/os_windows.rh` か `fs/os_posix.rh` に解決する。
   言語の追加はモジュール解決だけで最小。分岐の単位がファイルなので、差分が大きい箇所に向く。
2. **宣言の修飾（Rust 型）**: `cfg^(windows) let^ open = ...`。項目単位で、名前解決の前に外す。
   同じ名前を条件ごとに書ける。条件の式（`windows`・`os^ = "linux"`・`all^`/`any^`/`not^`）の文法が要る。
3. **コンパイル時の `if`（Zig・Nim 型）**: `when^ os^ = "windows" { ... }`。文・式の位置でも使える。
   選ばれなかった分岐を検査するか（Rust の `cfg!` 型）、解析しないか（Zig 型）を決める必要がある。

いずれでも、条件の値は `rhat build` のターゲットから決め、LSP は既定でホストのターゲットで解析する。
利用者の選ぶ機能（Rust の `feature`）を入れるなら、`--cfg NAME` のようなコマンドラインの指定と組で考える。

## 決めること

- 1〜3 のどれか、または 1 と 2 の組み合わせにするか。
- 条件に使えるキー（`os`・`arch`・ポインタ幅・機能）と、その綴り。
- 選ばれなかったコードを型検査するか。検査すれば別 OS 向けの壊れに早く気づけるが、その OS にしかない C 関数の宣言が要る。
- 分割コンパイルのキャッシュキーにターゲットの条件を含めること（今もターゲットは含む）。
