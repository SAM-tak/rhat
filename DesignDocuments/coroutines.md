# コルーチンと非同期処理（設計案）

R^ のコルーチンと `await^` の設計案です。手順 1a まで実装済みです（[実装状況](#実装状況)）。それ以外の構文は仮置きです。

表層は L^ のコルーチン（`yield^` による推論、`await^` による明示の委譲、双方向の `yield^`）をそのまま引き継ぎます。
L^ の `c^{R -> Y -> T}` 型は、R^ では `std.sys` のコルーチン型（`CoroutineNR<Y, T>`・`CoroutineR<R, Y, T>` など）に置き換えます。
中身は Goose の設計ノート
`../goose/docs/design/coroutines.md`（2026-10、未実装）と同じく、**stackless で、フレームを固定長の値として扱う**方式にします。
スケジューラ・イベントループ・タイマー・Channel 待ちは言語に入れず、ライブラリで作ります。

L^ のコルーチンより制限は多くなります。自由なコルーチンが必要なら L^ を使う、という分担を前提にしています。

## 実装状況

手順 1a（v1 の核）・1b・2・3（名指し）を実装しました。

- `yield^ e` / `yield^`（文として）。`yield^` を含む `p^` / `f^` は yieldable と推論され、呼ぶとフレームが返ります。
- フレームは組み込みの型で、表示は関数の返り値型として書く形（`py.ReturnType^`、多重定義などでは `overload^py(i32^).ReturnType^`）です。`start()`・`resume()`（`Y | T` を返す）、`done()`・`result()` を持ちます。
  状態の誤り（二重の start、未開始・終了後の resume、未終了の result）は実行時エラーです。
- 本体は再開関数に下ろし、入口でタグにより分岐します。中断点の後で読まれうるスロット（IR 上の生存解析）・引数・
  1回分の答えだけをフレームに置き、残りは `alloca` です。フレームへのポインタは `noalias` です。
- 中断点の規則 1・2・4 を検査します。yieldable な関数の呼び出しはフレームを作るだけなので、本体が `p^` でも
  関数の型は `f^` です（`p^ x:i32^ { yield^ … }` は `f^ i32^ -> py.ReturnType^;`）。本体の種別は `start`・`resume` に載り、
  `p^` のフレームを進めるには `p^` が要ります。
  フレームは値としてコピーでき（フォーク）、`let^` のフレームは進められません。
- 再開時の値 R: `var^ x:T = yield^ v` で受け取り、`c.resume(v)` で渡します。受け取らないコルーチンは `c.resume()` です。
- `std.sys` のコルーチン型（[フレーム型とコルーチン型](#フレーム型とコルーチン型)）: `ref^` で受ければフレーム型ごとに特殊化、
  `dynamic^` で受ければ種類の違うフレームを混ぜられます。yieldable の返り値に書けば、R・Y・T を推論の手がかりにし、
  本体と照合します。

- `await^`（[`await^`](#await)）、`for^ in^` でフレームを回すこと（[`for^ in^` で回す](#for-in-で回す)）。
- 中断点を跨ぐ Disposable（[Disposable](#disposable)）。フレームを捨てると、中断位置で生きているものを逆順に解放します。
- yieldable な `f^mutable^self^` メソッドのフレームを `f^` から進めるときの検査（receiver が借りた先なら拒否）。
- フレームが `--frame-warning`（既定 4096 バイト）を超えると警告します。
- フレーム型の名指し: `count.ReturnType^`・`overload^count(i32^).ReturnType^`（[typeof.md](typeof.md#関数の返り値型returntype)）。
  構造体のフィールドや配列の要素にフレームを置けます（`var^cs:count.ReturnType^[max^4] = {}`）。
- 1回分の答え `Y | T` は1つの合併型に平らになっています。`result()`・`await^`・`for^ in^` が Y や T を取り出すとき、
  それ自体が合併型なら、腕ごとにタグを判定して詰め直します（Y と T に同じ型があっても、どちらとして読むかは `done()` で決まります）。

- 自分のローカルを借りた内側のフレームの `await^`（[再貸し](#再貸し)）。

まだ拒否しているもの:

- 中断点を跨ぐ参照の場所（別名スロット）。
- 再貸しで受け取った参照を、内側がさらに別のフレームへ渡す `await^`、派生した参照を跨いで持つ内側。
- フレームのスレッド転送。
- ループの範囲バージョニングはコルーチンの本体には適用しません（ループを複製すると再開点が重複するため）。

## 要点

- `yield^` を含む関数は yieldable と推論されます。キーワードは付けません（L^ と同じ）。
- yieldable な関数を呼ぶと**フレーム**が返り、本体は一行も走りません。フレームは固定長の値です。
- フレーム型は関数ごとの無名の公称型で、`std.sys` のコルーチン型（`CoroutineNR<Y, T>` など）を満たします。
  `ref^` で受ければ特殊化、`dynamic^` で受ければ動的ディスパッチです（[dyn.md](dyn.md) と同じ）。
- `await^ c` は内側のフレームを外側のフレームの中に展開して委譲します。値は内側の返り値 `T` です。
- 中断点では、所有値・自分のローカルを指す借用・未着の所有返り値を生かしておけません。
  再帰呼び出しに課している制約（[design.md](design.md) の再帰の規則）を中断点に広げたものです。
- フレームは自身が保持する `Disposable` を知っており、捨てると中断位置に応じて `dispose` を走らせます。
- 実行時の仕組み（ヒープ確保・waker・間接呼び出し・スレッドローカル）は追加しません。
  コルーチンを使わないプログラムの生成コードは変わりません。

## 他の言語との位置関係

- **Rust**: stackless のステートマシンで、遅延開始・静的サイズ・実行器はライブラリ、という点は同じです。
  自己借用を中断点で禁止するため `Pin` は不要です。waker も持ちません。
- **Go**: stackful の goroutine はスタックを複製して伸ばすため、ポインタの再配置が必要です。
  R^ の参照は生アドレスで、データスタックは動かないので採れません。
- **Zig**: 旧設計（0.10）は yieldable を呼び出しを跨いで暗黙に推論し、伝染が見えなくなって削除されました。
  L^ の推論は本体の中で閉じており、呼び出しは伝染しない（呼ぶとフレームが返るだけ）ので、同じ問題は起きません。
  新設計（`std.Io` を引数で渡す）の「スケジューラを呼び出し側が選ぶ」考え方は、ライブラリ層で採れます。
- **Odin**: 言語に async を持ちません。言語を小さく保つという方針は共有しますが、
  手書きのステートマシンが明らかに劣る用途（接続ごとの処理、ゲームの複数フレームにまたがる処理、生成器）があるので、R^ では持ちます。

関数の色分けは R^ にも残ります。ただし L^ と同じく、印を書いて回る手間は推論で消え、
「呼ぶだけ」「同期的に回す」は色を問わず書けます。最初から非同期の作法をコルーチンに統一するので、
C# のようにコールバック方式と二重に存在する問題も起きません。

## stackful を採らない理由

stackful（タスクごとにスタックを持つ方式）は書き手にとって最も楽ですが、R^ のメモリモデルとは合いません。

- **データスタックはタスクごとに持てない。** 1本あたり 1 GiB の仮想アドレスを予約します（[threads.md](threads.md)）。
  タスクごとに必要本数ぶんを予約すると、数千タスクでアドレス空間が尽きます。サーバーは 10⁵ 単位の接続を待たせます。
- **データスタックは動かせない。** 参照は生アドレスで、伸長しても領域は移動しないという前提に立っています。
  Go のように複製して伸ばすことはできません。
- **ネイティブスタックの切り替えには環境ごとのアセンブリが要る。** stackless は通常の関数とデータ構造だけで書けます。

stackless の方式でも、中断中のフレームはネイティブスタックもデータスタックも保持できません。
データスタックの番号は静的に割り当てるので、同じ関数のフレームが2つ中断していると番号が衝突し、
スタック上の寿命が入れ子になるという前提が崩れます。中断中のフレームが持てるのは**固定長の値だけ**です。

## 宣言と型

### yieldable の推論

`yield^` か `await^` を本体に含む `p^` / `f^` は yieldable です（L^ の [syntax.sub.yieldable]）。
出す型 `Y` は本体の `yield^`（`await^` の委譲先も含む）を単一化して決め、食い違えば型エラーとします。
受け取る型 `R` は `yield^` の値を受ける束縛の注釈から決まります。最終結果の型 `T` は本体の `return^` から推論します。

```rhat
let^serve = p^conn:ref^Conn {
    var^ev:Event = yield^ Wait{fd = conn.fd}    # 待つものを値として出し、再開時に Event を受け取る
    ...
    return^true^
}
```

### 返り値の注釈は呼び出しが返すもの

`->` は、本体の宣言でも関数型の注釈でも、**呼び出したときに返るもの**を表します。
yieldable な関数の呼び出しはフレームを返すので、返り値を明示するなら `std.sys` のコルーチン型を書きます。
最終結果の型 `T` だけを書く `-> bool^` はエラーです。

```rhat
let^serve = p^conn:ref^Conn -> std.sys.CoroutineR<Event, Wait, bool^> {
    var^ev = yield^ Wait{fd = conn.fd}           # R is declared above, so no annotation here
    ...
    return^true^
}
```

- 書いたコルーチン型は、本体の `yield^`・`await^`・`return^` から求めた形と照合し、食い違えばエラーです。
  書いた R・Y・T は推論の手がかりにもなります（`yield^ 1` を `CoroutineNR<i64^, …>` なら i64^ と読みます）。
- `CoroutineR<R, …>` で R を書いた場合は、`yield^` の値を受ける束縛の注釈を省略できます。
- 実際の返り値型は無名のフレーム型で、コルーチン型はそれが満たす型です。
  Rust の `-> impl Future<Output = T>` と同じく「この基底型を満たす何か」を言うだけで、型を消去しません。
  具体的なフレーム型は `serve.ReturnType^` で得ます。
- フレームを返す普通の関数（`return^ serve(c)` だけを書く包み関数など）も、同じくコルーチン型を書きます。
  関数型の注釈 `p^ref^Conn -> std.sys.CoroutineR<Event, Wait, bool^>;` も同じ読みです。

Rust・Python・Kotlin は本体側に最終結果の型だけを書きますが、それで困らないのは `async`・`suspend` の印で色を明示しているからです。
R^ は yieldable を推論するので印がありません。返り値に書くコルーチン型が、コルーチンであることを書き手が明示し、コンパイラに守らせる唯一の場所になります。

- コルーチン型を書いた関数から `yield^` を消すと、宣言の時点でエラーになります。
- `-> bool^` と書いた関数に `yield^` を足すと、宣言の時点でエラーになります。呼び出し元を見て回る前に色の変化に気づけます。
- `->` の意味が一つなので、注釈と `ReturnType^` が常に一致します（C# の `async Task<T>` と同じ側です）。

明示する必要がなければ、注釈を省略して推論に任せます。

L^ も同じ規則です（[syntax.type.coroutine-result]）。L^ では `-> c^{ … }`、R^ では `-> std.sys.CoroutineNR<Y, T>` などと書きます。

### フレーム型とコルーチン型

フレームの大きさは、`R`・`Y`・`T` よりも本体で決まります。
引数、中断点を跨ぐローカル、`await^` で埋め込む内側のフレーム、状態タグ、返り値の置き場を持つからです。
`R`・`Y`・`T` が同じでも、本体が違えば大きさは違います（Rust で `async fn` ごとに無名の型ができるのと同じ事情です）。
したがって `R`・`Y`・`T` だけで決まる値の型は作れません。

そこで型を2層に分けます。

- **フレーム型**: yieldable な関数ごとにコンパイラが作る無名の公称型です。値として格納できます。
- **コルーチン型**: `std.sys` の5つの抽象型です。フレーム型は、R の有無と本体の種別に合うものを自動で満たします。

```rhat
public^def^Coroutine<T> {                               # every frame
    abstract^done:f^self^ -> bool^;
    abstract^result:f^self^ -> T;
}
public^def^CoroutineNR<Y, T> : Coroutine<T> {           # receives nothing
    abstract^start:p^self^ -> Y | T;
    abstract^resume:p^self^ -> Y | T;
}
public^def^PureCoroutineNR<Y, T> : CoroutineNR<Y, T> {  # ... of an f^ body
    override^abstract^start:f^mutable^self^ -> Y | T;
    override^abstract^resume:f^mutable^self^ -> Y | T;
}
public^def^CoroutineR<R, Y, T> : Coroutine<T> {         # receives an R at each yield^
    abstract^start:p^self^ -> Y | T;
    abstract^resume:p^self^, value:R -> Y | T;
}
public^def^PureCoroutineR<R, Y, T> : CoroutineR<R, Y, T> {
    override^abstract^start:f^mutable^self^ -> Y | T;
    override^abstract^resume:f^mutable^self^, value:R -> Y | T;
}
```

- R を受け取らないフレームは `CoroutineNR<Y, T>`、受け取るフレームは `CoroutineR<R, Y, T>` を満たし、どちらも `Coroutine<T>` を満たします。
  `resume` は型ごとに1つなので、dyn^ の表に多重定義を載せる規則は要りません。
- f^ 本体のフレームは `Pure` 版も満たします。`Pure` 版は一般版を合成するので、`ref^CoroutineNR<Y, T>` を受ける手続きには
  p^ 本体と f^ 本体のどちらのフレームも渡せます。`Pure` 版は進める操作を `override^abstract^` で
  `f^mutable^self^` に宣言し直します（[design.md](design.md)）。
- 適合は型引数で決まります。フレームはこれらの型を合成するのではなく、R・Y・T と本体の種別で満たします。
  Y と T は広がる先でもよく（`Error.A | nil^` を返すフレームは `CoroutineNR<i64^, nil^ | Error>` を満たします）、
  dyn^ の表の転送メソッドが答えを広げます。R は一致が要ります。

使い方は [dyn.md](dyn.md) の `Shape` と同じです。

```rhat
import^std.sys

# Specialized per concrete frame type: no indirect calls.
let^drive = p^co:ref^std.sys.CoroutineR<Event, Wait, bool^> { ... }

# Mixing frame types: a {data, method table} pair per element; frames live elsewhere.
var^tasks:std.sys.CoroutineR<Event, Wait, bool^>[dynamic^grow^] = {}
```

- `ref^` で受ける関数は、渡されたフレーム型ごとに特殊化します。
- `dynamic^` は種類の違うフレームを混ぜて扱えます。フレームの実体は別の場所（具体型の配列など）に置きます。
  dyn^ の表のために、フレーム型ごとに、フレームの組み込みメンバへそのまま渡すメソッドを持つ def^ をコンパイラが作ります。
- 値として格納する場所（ローカル・配列の要素・構造体のフィールド）には具体的なフレーム型が要ります。
  フレーム型は関数の返り値型なので、`serve.ReturnType^` で名指せます（[typeof.md](typeof.md#関数の返り値型returntype)）。
  多重定義された関数なら `overload^serve(ref^TcpConn).ReturnType^` で候補を選びます（[overloads.md](overloads.md)）。
  関数本体の中では `typeof^(serve(conn))` も使えます。
- 型を消去してヒープに置く形（Rust の `Box<dyn Future>`）や、最大サイズを型に持たせる形は採りません。

L^ の `c^{R -> Y -> T}` は構造的な型で、どの本体のコルーチンでも同じ型の値として扱えます。
これは L^ のコルーチンが GC 下のオブジェクトだからできることです。
R^ では「具体型は公称、共通の扱いは抽象型」という既存の形に寄せます。

### 複数のフレームをまとめて回す

種類の違うフレームを合併型の配列に入れると、要素は一番大きなフレームの大きさになります。
32 バイトのフレームと 1000 バイトのフレームを混ぜた 16 要素の配列は、約 16KB を取ります。

フレームの実体は種類ごとの配列に置き、まとめて回す一覧はコルーチン型の `dynamic^` 参照で持ちます。
回す側が関心を持つのは `R`・`Y`・`T` だけなので、合併型を定義する必要もありません。

```rhat
var^as:coA.ReturnType^[max^16] = {}
var^cs:coC.ReturnType^[max^2] = {}    # the large kind gets a pool of its own size
var^active:std.sys.CoroutineR<Event, Wait, nil^>[dynamic^max^18] = {}

as.push(coA())
active.push(ref^as[as.len - 1])
for^c in^active { c.resume(ev) }
```

- 大きなフレームは、その種類の配列の分だけ領域を取ります。
- 再開は dyn 経由の間接呼び出しになります。種類の揃った配列を直接回すなら直接呼び出しです。
- 配列の縮小などで参照が無効になる操作は、通常の借用の規則で拒否されます。添字で持つこともできます。

### `for^ in^` で回す

`for^ in^` は範囲・配列・カーソル（`iter()` と `next()` を持つ値）に加えて、**フレーム型を4つ目の形**として認識します。
フレームをカーソルの規約に乗せると、`iter()` が中断中のフレームのコピーになり（`Disposable` を持つフレームはコピーできません）、
`nil^` で終わる規約が `Y` に含まれる `nil^` と衝突し、変数のフレームを回してもコピーしか進まないからです。

```rhat
for^ v in^ walk(t) { print^(v) }   # a temporary frame, held by the loop
var^ c = walk(t)
for^ v in^ c { if^ v = 3 { break^ } }
let^ rest = c.resume()             # c itself advanced; the loop did not copy it
```

- 一時値のフレームはループが持ち、変数のフレームは `ref^` で借りてその場で進めます。コピーはしません。
- 1回目は `start()`、以降は `resume()` を呼び、`done()` で止めます。`nil^` は終わりの合図に使わないので、`Y` に `nil^` が入っても途中で止まりません。
- 出した値 `Y` を名前に束縛します。`Y` がタプルなら、カーソルと同じく `for^ a, b in^ …` で分解します。
- 再開時に受け取る値 `R` を持つフレームは回せません（`for^` は渡す値を持たないので）。エラーにします。
- 最終結果 `T` は束縛しません。変数のフレームなら、ループの後に `c.result()` で読めます。
- yieldable な `iter()` もそのまま動きます。`for^ x in^ obj` で `obj.iter()` がフレームを返し、それを4つ目の形として回します。
  L^ で `iterate` を yieldable にして書く反復子は、R^ でも同じ形で書けます。
- `f^` の中で回せるかは、進める操作の種別と受け手の参照先の規則（[`f^` のコルーチン](#f-のコルーチン)）で決まります。

### 生成と操作

呼び出しはフレームを返し、本体は走りません（L^ の [syntax.sub.no-contagion]）。
メンバは L^ と同じ名前にし、コルーチン型の抽象メンバとして宣言します。

- `c.start()`: 先頭から走らせ、最初の `yield^` か終わりまで進めます。
- `c.resume(v)` / `c.resume()`: 中断位置から続けます。`R` がないときは引数を取りません。
- `c.done()` / `c.started()`: 状態を問います。
- `c.result()`: 終わったフレームの返り値を読みます。終わっていなければ実行時エラーです。
- `c.dispose()`: 中断位置で生きている `Disposable` を解放して終わらせます（[Disposable](#disposable)）。
- `save()` / `load()` は持ちません。フレームが値なので、コピーと代入がそのまま同じ働きをします
  （コピーできるフレームに限ります）。

`start()` / `resume()` の返り値は L^ と同じく `Y | T` です。
未開始のフレームへの `resume`、開始済みのフレームへの `start`、終わったフレームの再開は実行時エラーです。
検査はフレームの状態タグの分岐に含まれるので、追加のコストはありません。

### `f^` のコルーチン

`f^` も `yield^` できます。動機は L^ と同じく反復で、何も書き換えない走査を `f^` のまま書けるようにします。

- **yieldable な関数の呼び出しは `f^` です。** 呼んでもフレームを作るだけで、本体は走らないからです。
  `p^` で書いた yieldable も関数の型は `f^` になり、`f^` から呼べます（L^ も同じ扱いです）。
- **進める操作の種別は本体に従います。** `f^` 本体のフレームの `start`・`resume`・`dispose` は `f^mutable^self^`、
  `p^` 本体のフレームのそれは `p^` です。`p^` のフレームは、本体が副作用を持つので `f^` から進められません。
  `await^` と `for^ v in^ c` も、書かれた呼び出しはなくても同じ判定を受けます。
- 一般のコルーチン型（`CoroutineNR`・`CoroutineR`）は進める操作を `p^` で宣言し、`Pure` 版は `f^mutable^self^` で宣言し直します。
  f^ 本体のフレームは両方を満たします（効果の少ない実装は契約を満たします。[design.md](design.md)）。
  `f^` は `ref^`・`dynamic^` で借りたフレームを書き換えられないので、`f^` が進めるのは自分のローカルや値で受け取った
  具体的なフレーム型の値です。`Pure` 版は「この生成器は純粋」と型で約束したいとき（返り値の注釈など）に使います。

L^ はこれに加えて「`f^` のコルーチンを進められるのは、その本体が作った場合だけ」「`f^` のコルーチンは、その本体から出てはならない」
という2つの規則を置きます（[syntax.sub.yieldable-f]）。L^ のコルーチンは GC 下の参照オブジェクトで、複数の持ち主が共有できるので、
外から来たものや外へ出たものを進めると、その跡が他の持ち主から見え、`f^` の参照透過性が壊れるためです。

R^ ではどちらも別の規則として置きません。フレームは値で、既存の規則から同じ結論が出ます。

- **借りたフレームは進められない。** 進める操作はフレームを書き換えます。`f^` は自分のローカル値なら書き換えられますが、
  `ref^` で借りた先は書き換えられません（`f^mutable^self^` の self に由来する先を除く。[design.md](design.md)）。
  値で受け取ったフレームはコピーなので、進めても呼び出し元には何も残りません。
- **フレームを返してよい。** 返すのは値で、呼び出し元は自分のコピーを持ちます。同じ引数からは同じフレームの値が返るので、
  `f^` の純粋性は保たれます。進めた跡は受け取った側のローカルにしか残りません。
  フレームが借用を持つなら、それがどこまで出られるかは通常の借用の規則が決めます。

フレームは参照をフィールドに持つ構造体の一種なので、進める権限は構造体と同じ規則で決まります（[design.md](design.md)）。

- `f^self^` の yieldable メソッド（読むだけのイテレータ）のフレームは、`self` への読み取り参照だけを持ちます。
  `f^` の中で借りた引数に対して `for^ x in^ obj` しても、書き換わるのはその `f^` のローカルであるフレームだけなので通ります。
- `f^mutable^self^` の yieldable メソッド（要素を取り除きながら出すイテレータなど）のフレームは、`self` への書き換え可能な参照を持ち、
  進めると self の先を書き換えます。`f^` からこれを進めるには、その先が `f^` のローカルでなければなりません。
  借りた引数を消費しながら走査するなら `p^` で書きます。

## `await^`

`await^ c` は、`c` の中断を外側の中断として外へ通し、外側の再開を `c` に届けます。
値は `c` の返り値 `T` です（L^ の [syntax.sub.await]・[syntax.sub.await-done]）。

```rhat
let^read_line = p^conn:ref^Conn, out:ref^u8[grow^] { ... }   # yields Wait, returns bool^

let^serve = p^conn:ref^Conn, line:ref^u8[grow^] {
    repeat^ while^ await^ read_line(conn, line) {
        handle(line[..])
    }
}
```

- 内側の `Y` は外側の `Y` と一致させ、内側の `R` は外側の `R` と一致させるか、内側に `R` がない形にします。
- 内側のフレームは**外側のフレームのフィールドとして埋め込みます**。ヒープ確保はありません。
  呼び出し式を `await^` すると、作ったフレームは外側のローカルになり、生存解析で外側のフレームに置かれます。
  フレームの大きさは `await^` の木全体から静的に決まります。
- したがって `await^` の辺で閉路を作るもの（自分自身を直接・間接に `await^` するコルーチン）は禁止します
  （「coroutine cannot hold a frame of itself」）。
  コルーチンから通常の再帰関数を呼ぶことは、中断点を跨がない限り構いません。
- `await^ co` のように既存のフレームの変数や参照を委譲する形は、そのフレームをその場で進めます。
  内側のフレームへの参照は中断のたびに取り直すので、外側のフレームの中を指すポインタは中断を跨ぎません。
- 内側のフレームが外側のローカルを参照している場合は、自己参照になるので拒否します（規則 4）。
- 内側が p^ のフレームなら、外側も p^ でなければなりません（進める操作の種別の規則と同じ）。

下ろしは次のループです。

```text
turn = frame を状態に応じて start / resume
L: frame が終わっていれば End へ
   内側の turn を Y として外側の turn に詰め、中断（外側の再開で戻る）
   外側に渡された値（R があれば）を持って frame.resume
   L へ
End: 内側の turn を T として式の値にする
```

### 高階関数を通す中断

`yield^` は字句的に一番内側の関数リテラルに属します（L^ と同じ）。HOF に渡した無名関数の中の `yield^` は、
その無名関数を yieldable にするだけで、外側のコルーチンを中断しません。HOF がそれを呼んでも、フレームが返るだけです。

```rhat
xs.each(p^ x { yield^ x })   # this p^ literal is the yieldable one
```

HOF に中断する処理を渡したいときは、その場で yieldable な無名関数を書き、HOF の側でそれを `await^` します。
HOF は yieldable 版として書き分けることになります（L^ の [syntax.sub.no-contagion] の「高階の手続きは色ごとに書き分け」と同じです）。
外側のコルーチンの中で反復しながら中断するだけなら、構文の `for^ x in^ xs { … yield^ … }` を使います。
`for^` は構文なので、カーソルはそのまま外側のフレームに入ります。

Goose（§2.4）はブロックを呼び出し先へ展開されるコードとして扱い、ブロック内の `yield` を外側のコルーチンの中断にします。
R^ は関数値を静的に解決し具体化するので同じことは実装できますが、関数リテラルとブロックで `yield^` の帰属が変わり、
L^ と食い違うので採りません。

## 中断点の規則

**中断点**は `yield^` と `await^` です。

1. **所有値を生かしておけない。** `T[grow^]`・`T[flex^]`・`T[]`・`T[max^]` など、データスタックに領域を持つローカル・引数・
   束縛のスコープ内では中断できません。中断の前に `do^{...}` でスコープを閉じるか、外の配列を借用して使います。
   [src/stacks.c](../src/stacks.c) の再帰検査（再帰成分への呼び出しで所有値を保持していたら拒否）と同じ判定を、中断点に対して行います。
2. **所有値の一時値・未着の返り値を生かしておけない。** 中断点を含む文の中で、所有値の一時値が評価済みで消費前、
   あるいは所有値を返す呼び出しの構築先が確保済みで値が未着、という状態は禁止します。
   再帰で許している「所有値の返却を構築先へ転送する」形は、中断を跨ぐと構築先のスタックが別の再開者に使われるので許しません。
3. **跨ぐローカルはフレームに入る。** 中断点を跨いで生きている固定長のローカルは、フレームの隠しフィールドになります。
   生存の判定は内部 IR 上の生存解析で行います（[下ろし方](#下ろし方)）。後で名前が出ても、その値が実際には使われないなら載せません。
4. **自分のローカルを指す借用は跨げない。** 再開時にローカルはフレームから別の場所へ戻るので、
   自分のローカル・引数のコピー・一時値を指す参照とスライスは中断点を跨いで使えません。
   通常の「局所参照の脱出」と同じ検査で、中断点をスコープの出口とみなします。
   外を指すもの（呼び出し元から借りた配列、グローバル、静的データ）は自由に跨げます。
   この規則によってフレームは自己参照を持たず、ただの値になります（Rust の `Pin` に相当するものが要りません）。
   例外は `await^` する内側のフレームへの貸し出しで、次の[再貸し](#再貸し)で扱います。
5. **`dispose` の本体では中断できない。** 破棄中のフレームには再開する相手がいません（L^ の `finally^` 内の `yield^` 禁止と同じ）。

`string^` はビューなので、規則 1 の対象ではありません。指す先が自分の所有値なら規則 4 で止まります。

### 再貸し

`await^ conn.read(buf[..])` のように、自分のローカル（`conn`・`buf`）を借りた内側のフレームを `await^` できます。

```rhat
let^echo = p^conn:net.TcpStream -> nil^ | net.Error {
    var^buf:u8^[4096]
    repeat^ {
        let^n = try^ await^ conn.read(buf[..])
        if^ n = 0 { return^ nil^ }
        try^ await^ conn.write(buf[0 .. n])
    }
}
```

内側のフレームは外側のフレームに埋め込まれ、外側の `await^` からしか進められません。外側のフレームが中断中に
（プールへの移動やコピーで）動くと、内側も一緒に動きます。ずれるのは「内側の引数スロットにある、外側のローカルを指すポインタ」だけです。

- 外側は中断のたびに、自分のフレームの位置をフレームの先頭（タグの後）に記録します。
- 内側を再開する直前に、内側の `ref^`・スライスの引数のうち、記録した位置から外側のフレームの大きさの範囲を指すものを、
  今の位置との差だけずらします。外から借りた参照は範囲外なので変わりません。
- コピーしたフレーム（フォーク）も、記録した位置が元のままなので同じ計算で正しく付け直されます。
- 貸し出したローカルは、内側が生きている間ずっと要るので、フレームに置きます（アドレスを取られたローカルはすべてフレームに置きます）。

条件（満たさなければ従来どおりエラー）:

- 内側は、受け取った引数そのもの以外に、引数から派生した参照（スライスの部分など）を自分の中断を跨いで持たない。
- 内側は、受け取った参照をさらに別のフレームへ渡して `await^` しない（入れ子の付け直しは v1 の範囲外）。
- 参照を持つ引数は `ref^` とスライスの直接の引数に限る。参照を持つ構造体の引数は不可。

Rust はこの問題を `Pin`（開始後のフューチャを動かせなくする）で解きます。R^ ではフレームを値のまま移動・コピー自由に保ち、
付け直しの費用（再開ごとに数命令）だけで済ませます。

伸長するデータを中断を跨いで持ちたいときは、Goose と同じく「外で所有して借用か添字で渡す」書き方になります。
サーバーなら、接続の受信バッファを呼び出し元の配列に置き、フレームはその参照か添字を持ちます。
バッファが中断中も同じ場所にあるので、io_uring や IOCP のような完了型 I/O にもそのまま渡せます。

## Disposable

フレームは、中断点を跨いで生きている `Disposable` なローカル（固定長で、規則 1 に掛からないもの）を保持できます。

- そのようなローカルを1つでも跨がせるフレーム型は、それ自体が `Disposable` になります。
- フレームの解放は状態タグで分岐し、**その中断点で生きている** `Disposable` だけを宣言の逆順で解放します。
  未開始・終了済みのフレームは何もしません（本体が終わるまでに通常の規則で解放済みです）。
- フレームの束縛がスコープを抜けるときなど、他の `Disposable` と同じ時期に解放されます。
  R^ は `dispose` を直接呼ぶことを許さないので、`c.dispose()` は持ちません。
- `await^` で待っている内側のフレームは、外側の解放に含まれます（内側の解放は内側の中断位置に従います）。

下ろしでは、生きている Disposable がある中断点ごとに解放ブロックを作ります。再開関数の入口の switch は、
解放要求の印（中断点の番号に `0x40000000` を足したタグ）でそのブロックへ飛び、解放してからフレームを終了させます。
- `Disposable` を含むフレームは暗黙にコピーできません（Channel のラッパーと同じ扱いです）。

Goose はデストラクタを持たないので「フレームは捨てるだけ」で済ませていますが、
R^ では中断位置ごとの後始末をコンパイラが生成します。どちらでも Rust の cancellation safety の問題は起きません。
中断中のフレームが持つ進捗は、外の配列に書いたものか、フレームが保持して `dispose` で後始末されるもののどちらかです。

協調的なキャンセルは再開値で伝えます（`Event.Cancel` を渡し、本体が `return^` する）。
言語の機能ではなく、ライブラリの約束事です。

## エラー

`try^` / `catch^` はそのまま使えます。`try^` による伝播は `return^` と同じくフレームを終わらせ、
`c.result()` がエラーの値を持ちます。`do^{... catch^: }` のブロックの中で中断しても、
エラーの移動はフレーム内で閉じているので問題ありません。

## スレッドとの組み合わせ

- フレームは、それを再開したスレッドで走ります。切り替えは中断点でしか起きないので、
  同じスレッド上の複数のフレームが同じデータに触れても競合は起きません。
- スレッドのシャードは共有しないので、イベントループはワーカーごとに1つ置きます（thread-per-core）。
  Seastar・glommio・monoio と同じ構成で、言語のランタイムを持たずに成立します。
- フィールドがすべて転送可能なフレームは転送可能な値であり、Channel で別のワーカーへ送ってそこで再開できます（[threads.md](threads.md) の転送の規則に従います）。
  借用を持つフレームは送れません。Go のようにタスクを暗黙に移す仕組みは持ちません。
- 重い処理やブロッキング I/O はワーカーへ投げ、その結果を待つコルーチンとして待ちます。

### 標準ライブラリ: L^ の `std.task`・`std.async`・`std.channel` を踏襲する

インターフェースは L^ のものをほぼそのまま使います（L^ の 05-modules.md の `std.async`・`std.task`・`std.channel` の節）。

- **待ちは値として出す。** コルーチンは待つものの id を `yield^` し、ループが id と準備のできた事象を突き合わせて再開します。
  waker を持たない Goose の形（待つものを値で伝える）と同じで、値のフレームと合います。
  スケジューラは言語に入れず、L^ の `sample/async.lh` と同じく R^ で書きます。
- **Channel の待ち方は2通り。** `ch.demand()` はスレッドが眠り、`await^ ch.take()` はタスクが待ちます。`ch.awaitable()` は到着を告げる id です。
  L^ の `take()` はホストのコルーチンですが、R^ では R^ で書いた yieldable な手続きにします。
- **Task。** `std.task.async(gen())`（未開始のフレーム）と `std.task.async(p^ -> T { … })`（引数なしの手続き）、
  `await`・`done()`・`failed()`・`awaitable()`。型は L^ と同じく、フレームなら最終結果の型、手続きなら返り値型から決まります。

L^ との違いは次のとおりです。

- **横取りがありません。** L^ は予算で走りを分けて（[syntax.sub.split-run]）`yield^` の無いジョブも取り上げますが、
  R^ はネイティブコードなので、切り替わるのは中断点だけです。`yield^` しない長いジョブはワーカーを占有します。
- **タスクごとの機械が要りません。** L^ はタスクの状態を VM の機械ごと持ちます。R^ ではフレームそのものがタスクの状態で、大きさは固定です。
- **スレッドを跨ぐタスクは転送可能なフレームに限ります。** `std.task.async` に渡すフレームは、フィールドがすべて転送可能でなければなりません
  （[threads.md](threads.md)。L^ で carry できないものが `Refused` になるのと同じ位置づけです）。
  フレームは中断中にデータスタックを持たないので、転送可能ならどのワーカーで再開しても構いません。
- **タスクはランタイムの共有領域に置きます。** 種類の違うフレームを預かるため、大きさと再開関数を添えて移します。
  Channel の本体と送信済みメッセージがどのスレッドのデータスタックにも属さないのと同じ扱いです。
- **結果は転送の規則で渡します。** L^ は GC の管理を移譲しますが、R^ は [threads.md](threads.md) の転送の規則でエンコードして渡します。
- **待ちは通知で受けます。** L^ は待機集合を時計で見ますが、R^ は epoll・kqueue・IOCP の通知を使えます。インターフェースは変わりません。

ソケットとタイマーの API は [net.md](net.md) にあります。`run_blocking` は手順 5 で決めます。

## 下ろし方

フレームは構造体で、引数・跨ぐローカル・埋め込んだ内側のフレーム・返り値・状態タグを持ちます。
本体は1つの再開関数になり、入口でタグにより中断位置の直後へ分岐します。

- 中断点を跨ぐローカルは、最初からフレームのフィールドに置きます。再開関数はフレームへのポインタ越しに読み書きし、
  中断と再開のたびに書き出し・読み戻すことはしません。跨がないローカルは従来どおりの `alloca`（SSA）です。
- フレームへのポインタには `noalias` を付けます。中断点と中断点の間では LLVM がスカラーをレジスタに載せ、
  ロード・ストアをまとめるので、必要なところだけ書き出し・読み戻しをしたのと同じ結果になります。
- 区間の中でフレーム上のローカルを `ref^` で借りても、規則 4 により借用は中断で終わります。
  フレームを値としてコピー・移動するのは中断中だけなので、借用が古い場所を指して残ることはありません。
- どのローカルを載せるかは、内部 IR 上の生存解析で決めます。中断点で実際に生きている値だけがフィールドになります。
- 同時に生きていないローカル同士は、フレームの同じ領域を共有できます（スロットの重ね合わせ。Rust の最適化と同じ）。
  v1 の範囲外とし、後で入れます。入れるとフレームの配置が変わるので、そのときはインターフェースも変わります。
- `await^` の内側は外側の再開関数に展開するか、内側の再開関数を直接呼ぶかを選べます。どちらも直接呼び出しです。
- 再開関数は通常の関数と同じくデータスタックの基準位置を受け取ります。中断点で所有値が生きていないので、
  中断時のスタックの位置は入口と同じです。

Goose はこれを「中断で書き出し、再開で読み戻す」形で下ろします。C を出力するので、生成した C を読みやすく保ち、
レジスタ割り当てを C コンパイラに任せるためです。R^ は LLVM IR を直接出すので、その必要がありません。
LLVM のコルーチン機構（`llvm.coro.*`）は使わず、下ろし処理は自前で行います。

- CoroSplit は最適化（インライン化・SROA・不要コード除去）の後でフレームを組むので、フレームの大きさが最適化に依存します。
  -O0 と -O2、LLVM のバージョンでも変わり、フレームは呼び出し側の IR に直接入るので、ABI とインターフェースが不安定になります。
  デバッグとリリースの成果物を混ぜられず、インターフェースの early cutoff も最適化器の都合で外れます。
- 呼ばれる側を CoroSplit まで最適化してから呼び出し側の IR を作る、という関数単位の順序制約も入ります。
- 既定の ABI はフレームを確保関数で取ります。呼び出し元が固定長のバッファを渡す ABI（retcon。Swift が使います）もありますが、
  バッファの大きさは先に決める必要があり、上限を先に決めるならその分の領域は結局取られます。

llvm.coro で縮む分のうち効きの大きいもの（実際には使われない値を載せない、同時に生きていない値で領域を共有する）は、
内部 IR 上の生存解析と重ね合わせで自前で取れます。Rust もフレームの配置を LLVM ではなく MIR の段階で決めています。
取りこぼすのは、インライン化の後でないと消えない値です。

フレームの大きさが閾値（既定は 4KB 前後を想定。実装時に計測して決め、オプションで変えられるようにします）を超えたら警告します。
エラーにはしません。大きなフレームを少数持つ用途は正当だからです。警告は、大きなローカルを呼び出し元が持つ配列の借用に
置き換えることを促します。Rust の clippy の `large_futures` と同じ考え方です。

フレームの配置は本体から決まり、呼び出し側の IR（フレームを置く場所の大きさ）を直接変えます。
分割コンパイルでは、フレームの配置と性質をモジュールのインターフェースに含め、変わらない限り依存側へ波及させません
（[separate_compilation.md](separate_compilation.md)）。

## L^ との差

- 所有値・自分のローカルへの借用・未着の所有返り値は中断を跨げません（L^ には制限がありません）。
- `await^` の閉路（再帰的な委譲）は書けません。
- `c^{R -> Y -> T}` の代わりに、フレーム型ごとの公称型と `std.sys` のコルーチン型を使います。
- 予算による実行の分割（L^ の [syntax.sub.split-run]）はありません。ネイティブコードなので、中断は `yield^` だけです。
- `save()` / `load()` はフレームのコピーで代わります。
- `f^` のコルーチンに「作った本体だけが進められる」「本体から出さない」の規則を置きません。値の意味論と `f^` の効果制限から従います。
