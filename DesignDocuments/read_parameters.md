# `read^` 引数の検討案（未実装）

現時点では実装を見送ります。この文書は将来の設計検討のための記録であり、
現在の構文・型検査で `read^` を使用できるという意味ではありません。

## 目的と基本方針

`p^` の参照引数は、現状どおり既定で借用先を変更できるものとします。
必要な引数だけを読み取り専用にする指定として、`immutable^` や `const^` よりも
「読むために渡す」という用途が分かりやすい `read^` を名称案とします。
引数宣言内での位置は未確定です。例えば次の表記を検討します。

```rhat
# 構文案。現在は使用できない。
let^inspect = p^read^input:ref^Data, output:ref^Buffer {
    # input を読み、output を変更する。
}
```

通常の `f^` は既に借用先を変更できず、`p^` も呼べません。
演算子の自動借用にもこの既存の効果制限を使い、`read^` の導入を前提にしません。
既存の `f^mutable^self^` を維持するかどうかは、この案とは別の判断です。

## 求める保証

以下の二つは異なる保証です。

1. 指定した引数を経由する変更だけを禁止する。別のエイリアスによる変更は許す。
2. 指定した領域が呼び出し中に変化しないことを保証し、別のエイリアスによる変更も禁止する。

採用するなら、単なるアクセス経路の制限で終わらせず、後者を目標とします。
例えば上記の手続きに同じ領域を `input` と変更可能な `output` の両方として渡す場合は、
読み取り専用の保証を破る可能性があるため拒否します。
他の引数、既存の参照、内部参照、手続き間で転送された参照や、
暗黙に渡されるトップレベル変数の参照も検査の対象です。

オブジェクトを永久に不変にする仕組みとは分け、初版は呼び出し中の保護に限定する案です。
読み取り専用の借用をいつ開始するかは、左から右の引数評価と合わせて決める必要があります。
後続引数の評価中に保護対象を変更するケースも、仕様と検査に含めます。

## 実装上の課題

既存の借用元追跡 `Roots`、寿命検査、配列の縮小時のエイリアス検査を土台にできます。
ただし、現在の寿命・効果検査だけで上記の保証が成立するわけではありません。

- 読み取り専用の借用期間と、重なる領域への変更経路を追跡する。
- フィールド、配列要素、スライス、内部参照を通る操作について、保護範囲を定義する。
  直接の保存領域と、参照フィールドの指す別オブジェクトの扱いも決める。
- 参照のコピーや別の手続きへの転送で、制限が失われないようにする。
- 再帰、オーバーロード、関数の契約、`dyn^` の呼び出しに規則を適用する。
- 外部関数が参照先を変更する可能性を、外部宣言の契約として扱う。
  外部コード自体の正しさを R^ の静的検査だけで保証するものではない。
- 戻り値に参照・スライスが含まれる場合、呼び出し後の保護と寿命を定義する。
  初版では読み取り専用の借用の持ち出しを拒否する案も含めて検討する。

初版は借用元のオブジェクト全体を保守的に保護し、変更可能な引数との重なりを拒否する案です。
同じオブジェクトの別フィールドを独立に扱う精度向上や、実際には変更しない引数を許す効果解析は、
追加の検討事項とします。不必要な拒否の削減は、保証を弱めずに進める必要があります。

## 導入する場合の順序

1. 保護する領域、借用期間、エイリアスが重なる場合の規則を確定する。
2. 直接の代入、変更メソッド、手続きへの転送を保守的に検査する。
3. スライス・内部参照・再帰・動的呼び出し・外部関数との整合を検証する。
4. 寿命、引数の評価順、制限の持ち出し、LSP の表示・診断を回帰テストで確認する。
5. 必要に応じて保護範囲の精度を上げ、正しいコードの不要な拒否を減らす。

修飾子を構文として追加するだけの変更ではなく、借用検査の機能追加として扱います。
