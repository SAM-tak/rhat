# スレッドと Channel の実装プラン

`std.thread` と `std.channel` を実装済みです。OS スレッドごとに独立したデータスタックの
シャードを構築し、インスタンスとして作る `Channel<T>` で通信します。
下の実装プランは設計理由と残る拡張を含みます。現在の公開 API と制限は次のとおりです。

## 現在の公開 API

- `std.channel.Channel<T>.new(messages, bytes) -> Channel<T> | std.channel.Error`
- `ch.clone() -> Channel<T>`、`ch.close()`、スコープ終了による保持の解放。
- `ch.send(ref^value)` / `ch.try_send(ref^value) -> nil^ | std.channel.Error`
- `ch.receive()` / `ch.try_receive() -> Message<T> | Closed | Empty`
- `std.thread.spawn(worker, ref^args) -> Thread | std.thread.Error.StartFailed`
- `thread.join()`、スコープ終了による自動 join、`std.thread.hardware_threads()`。
- `std.thread.sleep(seconds:f64^)`。L^ と同じ秒単位で、`sleep(0.2)` は200ミリ秒。
- `std.thread.current_id() -> i64^`、`thread.id() -> i64^`。

スレッド ID は OS のハンドルやネイティブ ID とは別の、プロセス内で一意の正の整数です。
メインスレッドも取得でき、同一スレッドでは常に同じ値を返します。終了後も ID を再利用しません。
ワーカーが取得する `current_id()` と、起動元の `Thread.id()` は一致します。
`Thread` は ID を保存するため、`join()` 後も同じ値を返し、既定構築した未起動の値ではゼロです。
`current_id` は初回に ID を割り当てることがある `p^`、`id` は保存値を読む `f^` です。

`sleep` は呼び出した OS スレッドを待機させる `p^` です。有限のゼロ以下の値は即座に戻り、
NaN・無限大はランタイムエラーです。ゼロに yield の意味は持たせません。
実際の精度と再開時刻は OS とスケジューラに依存し、タスクのサスペンドには使いません。
通常の `externC^rh_thread_sleep` を介し、Windows はミリ秒へ切り上げて待機、
POSIX はナノ秒へ切り上げて `nanosleep` を呼び、シグナルで中断された残り時間は再度待機します。

`Message<T>.value` に受信値が入ります。ブロッキング receive は `Empty` を返しませんが、
両受信操作は同じ結果型を使います。`nil^` 自身も `Message<nil^>` で届くので空とは区別できます。
生成した Channel を暗黙コピーせず、必要な保持を `clone()` で作って起動引数へ入れます。
既定構築した Channel は閉じた空のハンドルであり、clone・close・dispose も安全です。

`Error` は公称のエラーグループです。`Error.Full` など個別の種類を調べるときは、
先に `fits^std.channel.Error` でグループへ絞り込みます。通常は `try^` で伝播できます。
ワーカーの結果は値なし、または `nil^` とエラーの合併に限ります。
ワーカーから未処理のエラーが返るとプロセスを診断終了します。

固定サイズ値・所有配列・それらの構造体と合併の転送、容量予約、close と待機解除、
シャードの作成と破棄、同一スレッドへの C コールバックに対応します。
所有配列は長さと内容を転送し、`max^` の受信容量は転送時の長さになります。
起動引数用にスタック番号 0 を確保し、ワーカーの通常の配置は番号 1 から始めます。
現在は全入口を覆う共通の最大スタック数を各シャードに予約します。

Windows と POSIX の実装を持ちます。時間制限、select、名前付き Channel、タスクによる待機、
外部スレッドからの R^ 呼び込みには未対応です。Channel を含むメッセージは今後も禁止します。
実行例は [examples/threads.rh](../examples/threads.rh) を参照してください。

## 採用するモデル

- スレッドは自分のデータスタック、実行コンテキスト、後始末を持つ。
- 普通の R^ の所有値・参照・スライスは、そのスレッドの中に留める。
- Channel 本体と送信済みメッセージは、どのスレッドのデータスタックにも属さない。
- 送信は独立したメッセージへのコピー、受信は受信側の所有値への再構築とする。
- Channel は型ごとに一つではない。同じ `Channel<Job>` を実行時に何個でも作り、
  起動引数としてワーカーへ渡せる。
- 最初は OS スレッドによる同期 API を実装する。タスクスケジューラとコルーチンは別の計画とする。

Channel の動的な個数は、データスタックの静的割り当てとは衝突しません。
コンパイラが決めるのは「一つの実行に必要なスタック数」で、実行時に決まるのは
「その構成を持つシャードと Channel 本体の個数」です。
ただし、通常の配列記述子をそのまま他スレッドに渡してよい、という意味ではありません。

## 現状から必要になる変更

現行の [メモリモデル](design.md) は、所有値の生存期間と呼び出しグラフからスタック数を決め、
隠れた基準位置を関数に渡します。配列記述子は所有スタックへのポインタを含みます。

- `src/llvm.c` は静的な `@rh_stacks` 表を出力し、そこからスタックを選ぶ。
- `runtime/rhat_runtime.c` はプロセス共通の `rh_stacks` / `rh_stack_count` を持つ。
- Windows の障害ハンドラもその表を走査する。
- C コールバックの `rh_callback_sp` もプロセス共通である。
- トップレベル束縛は隠れた参照や実行コンテキストから参照する。

この状態で OS スレッドだけを追加すると、異なる実行が同じスタック先端や束縛を書き換えます。
スタック表の分離に加えて、入口の検査と境界でのコピーが必要です。

## スレッドごとのシャード

ランタイム内部に `RhThreadContext` を設け、少なくとも次を持たせます。

| 状態 | 所有者 |
| --- | --- |
| `RhStack` の管理表・個数・各領域の予約 | そのスレッド |
| C コールバックのスタック基準位置 | そのスレッド |
| R^ の実行コンテキストと初期化状態 | そのスレッド |
| スタック配置、型情報、関数コード、読み取り専用リテラル | プロセス内で共有 |
| Channel の制御ブロック・ロック・メッセージ | ランタイムの共有領域 |

TLS は現在の `RhThreadContext` を指します。既存の隠れたスタック基準位置は維持し、
LLVM のスタック取得処理を「現在のコンテキストの表 + 基準位置」へ切り替えます。
シャード内の配列の通常操作にロックは追加しません。コンテキスト取得は関数入口でまとめ、
単一スレッドのプログラムでホットループの性能が落ちないか確認します。

スタック数はワーカー入口から同期的に到達する呼び出しを解析して決めます。
`spawn` の先は別の解析ルートであり、親の必要スタック数へ子の分を足しません。
再帰に関する現在の制約は各ルート内で維持します。ワーカーが自分と同じ入口を spawn
することは、同一シャード上の再帰とは区別します。
起動引数の再構築・終了処理・C コールバックに必要な分も配置に含めます。
最初の実装ではプログラム共通の最大必要数を各シャードに適用しても構いません。

現在の 1 スタックあたり 1 GiB の仮想アドレス予約をそのまま使うと、
予約量は「同時スレッド数 × 必要スタック数 × 約 1 GiB」になります。
予約と物理コミットは区別し、まず入口別の必要数と使用量を計測可能にします。
領域は生成時に予約し、アドレスの安定性と現在のガード領域の規則を維持します。

### Windows の障害処理と FFI

Windows の VEH はプロセスで一度だけ登録し、障害が発生したスレッドの TLS にある
シャードだけを走査します。ハンドラ内で共有表のロックやメモリ確保をしません。
管理外の障害は引き続き OS へ返します。シャードの解放はそのスレッドが R^ を
実行し終わってから行い、VEH の解除は全ワーカー終了後です。

`rh_callback_sp` はコンテキストへ移します。R^ から C を経て同じスレッドへ戻る
`exportC^` はそのコンテキストを使います。R^ が作っていない外部スレッドからの
呼び込みは、初版では未対応として入口で診断します。
TLS のないスレッドを暗黙に main のシャードへ接続してはいけません。

FFI は従来どおり信頼境界です。共有する C の資源を複数ワーカーから使う場合の
同期は C 側の契約に従います。標準ライブラリの I/O なども、スレッド内の状態と
プロセス共通の外部資源を区別して監査します。

## スレッドの入口とトップレベル束縛

`std.thread.spawn(entry, args)` は静的に解決できる `p^` を起動します。
スレッド生成そのものは `externC^` で宣言した C 関数が担当し、コンパイラは次の
橋渡し操作を提供します。任意のモジュールの `p^` 内で利用できます。

| 操作 | 結果と役割 |
| --- | --- |
| `thread_entry^(entry, ref^args)` | 入口を検査し、`externC^p^ref^std.sys.ThreadArgs;` 型の C 用ラッパーを生成 |
| `thread_transfer_type^(ref^args)` | 転送可能性を検査し、静的な `ref^read^std.sys.ThreadTransfer` 型の転送記述子を生成 |
| `thread_args^(ref^args)` | 借用関係を保ったまま、`ref^read^std.sys.ThreadArgs` 型へ引数ポインタを変換 |
| `thread_stack_count^()` | 実行コンテキストに必要なスタック数を `i64^` で取得 |

`ThreadArgs` と `ThreadTransfer` は `std.sys` の不透明な C 型です。
`std.thread` はこれらを使って通常の `externC^` 呼び出しを行います。

```rhat
import^std.sys
externC^rh_thread_spawn:p^entry:externC^p^ref^std.sys.ThreadArgs;,
    transfer:ref^read^std.sys.ThreadTransfer, args:ref^read^std.sys.ThreadArgs,
    stacks:i64^ -> i64^;

# Inside a p^ or template^p^ body:
let^worker = thread_entry^(entry, args)
let^transfer = thread_transfer_type^(args)
let^h = rh_thread_spawn(worker, transfer, thread_args^(args), thread_stack_count^())
```

標準の C 関数は成功時にハンドル、失敗時に `0` を返します。引数の読み取り・転送準備は
呼び出しから戻るまでに完了させ、子側は独立した実行コンテキストを接続して入口を呼びます。
親のデータスタックは共有しません。ハンドルは `rh_thread_join` に渡して回収し、
`std.thread.Thread` はこの管理を `Disposable` で包みます。

独自ライブラリは生成関数の C シンボル名も変更できます。コンパイラは生成関数の名前を
決め打ちしません。橋渡し操作の検査は維持されますが、消去した引数・入口・転送記述子の
型の一致や実行コンテキストの管理は FFI 側の契約です。異なる型の組を渡してはいけません。
対応する ABI は `runtime/rhat_thread.h` にあり、コンパイラと同じ版を使います。

`--thread-runtime PATH` または `RHAT_THREAD_RUNTIME` で標準のスレッド・Channel 用 C
ランタイムを差し替えられます。独自 OS 向けには必要に応じて `--runtime` で基礎ランタイムも
差し替えます。いずれもコンパイラ本体の再ビルドは不要です。

初版の入口は「受信側で構築した引数への借用を受け、通常の結果値を返さない処理」に限定します。
`nil^` とエラーの合併は許可し、未処理のエラーはプロセス終了として扱います。
一般の関数値の保存や、キャプチャ付きクロージャの実装を先行条件にしません。

- 親のローカル変数やその参照をキャプチャできない。
- トップレベル束縛を直接・間接に使う入口を拒否する。メソッドや動的ディスパッチ経由も検査する。
- 静的メンバの可変状態など、実行コンテキストに依存する状態も検査対象とする。
- コンパイラが共有可能と保証する不変の定数とリテラルは利用できる。
- 未初期化のトップレベル実行文を子で再実行したり、親の実行コンテキストを共有したりしない。

入口で必要な情報はすべて明示的な起動引数へ入れます。暗黙にグローバルを複製する
Goose の方針は採りません。違反は生成コードの実行時まで遅らせず診断します。

## シャード境界を越える値

境界を越せるかどうかは型から再帰的に判定し、利用者のライフタイム注釈は増やしません。
転送可能という性質は、通常のコピー可能性や C ABI の flat 判定とは分けます。

| 型 | 転送方針 |
| --- | --- |
| 数値、`bool^`、`char^`、`nil^`、対応する列挙値 | 値をコピー |
| 固定長配列・構造体・合併 | 要素・フィールド・有効な選択肢を再帰的に転送 |
| 所有配列 | 要素列をメッセージへコピーし、受信側のスタックに再構築 |
| 行を所有するジャグ配列 `T[max^N [grow^]]` | 行ごとのスタック群の再構築は未対応のため、構造体に含む場合も拒否 |
| `ref^`、読み取り専用参照、借用スライス | 拒否 |
| `string^` | ビューなので初版では拒否。所有バイト配列で運ぶ |
| 通常の `Disposable`、ファイル、外部ポインタ、関数値 | 初版では拒否 |
| Channel ハンドル | 起動引数でのみ、ランタイムの保持数を増やして転送 |
| Thread ハンドル | 拒否 |

読み取り専用でも、参照先の寿命が親のシャードに依存することは変わりません。
文字列リテラルだけを特例にして `Channel<string^>` を許すこともしません。
文字列を送る便宜関数は借用ビューから所有バイト配列へコピーする操作として後から追加できます。

初版のマイルストーンは固定サイズの転送から始めますが、実用版には所有配列の転送まで含めます。
構造体の所有フィールド数など、現行の型配置の制約は広げません。
エラー値もメッセージにできるのは、その表現が同じ転送条件を満たす場合だけです。

### エンコードと再構築

コンパイラは具体的な型ごとに、サイズ計算・エンコード・デコードの補助処理を生成します。
メッセージには所有配列の記述子や送信元のアドレスを残さず、長さと内容を格納します。
これは同一実行ファイル内の内部形式で、保存形式やネットワークプロトコルにはしません。

送信中だけ元の値を借用します。送信完了後は送信元を変更・破棄でき、送信者が終了しても
キュー内の値は残ります。受信値は呼び出し側が用意した構築先へ直接デコードし、
そのスコープの通常の所有値になります。所有配列を含む結果を一時ランタイム領域への
参照として返してはいけません。

キューは型の実装情報も保持し、型を消したバイト列を利用者が差し込める API は設けません。
サイズ・アラインメント・乗算オーバーフローを検査し、失敗時は部分メッセージを解放します。
受信値の再構築中のスタック超過・コミット失敗については、現在のプロセス終了の規則を維持します。

## Channel の所有と API

`channel_handle^<T>` は要素型を持つ、不透明な低水準のハンドルです。整数との変換や
暗黙コピーはできず、スコープ終了時に保持を自動解放します。構造体や配列に格納した場合も
再帰的に解放されます。明示的な複製は保持を一つ増やし、各保持を独立に解放します。

次の組み込み操作は、任意のモジュールの `p^` 内で利用できます。`h` は
`ref^channel_handle^<T>` またはその読み取り専用参照、`value` は `ref^read^T` です。

| 操作 | 結果 |
| --- | --- |
| `channel_new^(T, messages, bytes)` | `channel_handle^<T>` を生成。確保失敗・不正な容量では空ハンドル |
| `channel_valid^(h)` | 確保済みかを `bool^` で返す。close 済みでも保持があれば true |
| `channel_clone^(h)` | 同じキューの保持を増やした新しいハンドル。空なら空を返す |
| `channel_close^(h)` | キューを閉じ、待機中の送受信を起こす。保持の解放とは別 |
| `channel_send^(h, value, blocking)` | 成功 0、closed 1、full 2、oversized 3、allocation failure 4 |
| `channel_receive^(h, blocking)` | `std.channel.Message<T> \| std.channel.Closed \| std.channel.Empty` |

容量と `blocking` は `i64^`、`blocking` の 0 は非待機です。受信操作を包む手続きには
上記の受信結果型を明示します。コンパイラは結果型の要素型がハンドルと一致することを検査し、
受信値を呼び出し側の構築先に再構築します。空ハンドルの送受信は closed として扱います。

`std.channel.Channel<T>` はハンドルを private なフィールドに保持し、既存のメソッド API と
エラー型で包みます。独自ライブラリも同じ組み込み操作から実装できます。
要素型はハンドルから取得し、呼び出し元の型引数やモジュール名には依存しません。

`std.channel` は `Channel<T>` を公開します。作成時にメッセージ数と総バイト数の上限を
指定する、境界付き MPMC FIFO とします。同じ型でもインスタンスが違えば通信経路は別です。
一つのメッセージは一人の受信者だけが取得し、ブロードキャストにはしません。
競合する送信はロック下の確定順に並び、公平性は保証しません。

| 操作（概念上の署名） | 動作 |
| --- | --- |
| `new<T>(message_limit, byte_limit) -> Channel<T> \| Error` | 正の上限で作成 |
| `ch.clone() -> Channel<T>` | 同じ本体への独立した保持を返す |
| `ch.send(ref^read^ value:T) -> nil^ \| Error` | 空き容量を待ってコピーを受理 |
| `ch.try_send(ref^read^ value:T) -> nil^ \| Full \| Error` | 容量待ちをしない |
| `ch.receive() -> T \| Closed` | 値か、close 後の終端まで待つ |
| `ch.try_receive() -> T \| Empty \| Closed` | 到着待ちをしない |
| `ch.close()` | 以後の送信を拒否し、すべての待機者を起こす |

`Error` の候補は `InvalidCapacity`・`MessageTooLarge`・`Closed`・`OutOfMemory` とします。
ここでの `Closed` / `Empty` / `Full` は結果の区別を表す仮名です。
`T` が同じエラーや `nil^` を含んでも衝突しないよう、最終 API はタグ付きの
`ReceiveResult<T>` / `TryReceiveResult<T>` などで値と制御結果を包みます。
一般の `T` にゼロ値や番兵値を要求しません。

- `send` 成功はキューが値を受理したという意味で、受信側の処理完了は意味しない。
- `close` は冪等。受理済みの値は順に受信でき、空になってから `Closed` を返す。
- `send` と `close` の競合は同じロック下で確定する。close 後に追加される値はない。
- 大きすぎる値は待たずに失敗する。満杯時に送信値を先に無制限にエンコードしない。
- メッセージ数・バイト数の予約をロック下で行い、ロック外でエンコードしてから公開する。
  close・確保失敗時は予約を戻し、未公開のメッセージを破棄する。
- 受信者が取り出したメッセージは、その受信処理が再構築完了まで単独所有する。
  容量へ計上するキュー内・予約中の量と、再構築中の量は診断上区別する。
- `try_` は条件変数で待たないという意味で、ロック不要やメモリ確保不要は保証しない。
- メッセージ上限は内容のバイト数とし、管理用メモリの実測値も別に把握する。

時間制限付き送受信は次段階で追加し、単調時計の一つの期限を使います。
`peek`・`atomic`・名前付き検索・受信確認付き `supply`・複数 Channel の select は初版に含めません。
通常のロックは利用者へ公開せず、ロックを持ったまま R^ の処理を呼びません。

### Disposable と共有本体

Channel のラッパーは `channel_handle^<T>` を保持するため、暗黙コピーが禁止されます。
`Disposable` の合成や独自の `dispose` は不要で、ハンドルが自動解放を担当します。
`clone()` は明示的に共有本体の参照カウントを増やして新しいラッパーを作ります。
起動引数に含む Channel も、コンパイラが生成する転送処理で保持数を増やします。
通常の構造体コピーや任意の `Disposable` にこの操作を広げません。

ワーカーの起動引数は親で借用し、子のローカル所有値として再構築します。
Channel を含む非コピー型の引数でも、通常の値引数によるコピーを経由しません。
この専用境界処理はコンパイラの支援が必要で、既存の `externC^` だけでは実装できません。

スコープ終了はそのラッパーの保持を一つ返すだけで、共有本体を close しません。
最後の保持がなくなったら、残存メッセージと同期資源を破棄します。
操作中は借用元のラッパーが生存し、他の保持の破棄で本体が消えないことを保証します。
close は通信プロトコル、dispose は保持の解放という別の役割です。

**Channel を Channel のメッセージに含めることは恒久的に禁止します。** 構造体・配列・合併に
包んでも同じです。起動引数での受け渡しだけでワーカープールや動的なパイプラインは作れます。
キュー内に自分や相互の Channel を保持できるようにすると参照カウントの循環が作れるためです。
この禁止を将来の拡張予定には含めません。

## Thread ハンドルと終了

`std.thread` は `spawn`・`Thread.join()`・`hardware_threads()` を公開します。
`Thread` は非コピーの `Disposable` で、初版には detach を設けません。

1. 親が起動引数を検査・エンコードし、スレッド制御ブロックを確保する。
2. 子用シャードの予約までを spawn の成功条件とする。失敗時はすべて解放する。
3. 子の TLS を設定し、引数を再構築して入口を実行する。
4. 正常終了時は引数を含むローカル値を通常どおり解放し、子のシャードを解放する。
5. OS スレッドが完全に終了した後に join が戻り、ネイティブ資源も一度だけ解放する。

子用シャードの準備は親で行って子へ単独所有を引き渡す形を基本とします。
OS スレッド作成に失敗した場合は親がそのシャードを解放します。
spawn 用の予約処理は途中までの予約を戻せる形へ分離し、予約失敗を
`std.thread.Error.StartFailed` として親へ返します。OS スレッド作成失敗も同じ種類です。
これは従来の起動時予約の即時終了からの拡張です。
main の起動時予約と、実行開始後のコミット失敗の規則は維持します。
子の終了情報と OS ハンドルはシャード外の制御ブロックに置き、join まで保持します。

`join()` 後もラッパーは有効な「終了待ち済み」状態とし、再度の join は即座に戻ります。
dispose は未 join なら自動で join し、済んでいれば何もしません。
ワーカー自身の Thread ハンドルは転送できず、自己 join を公開 API から構成できないようにします。
処理結果は Channel で返し、`Thread<T>` による結果値の保持は後回しにします。

自動 join は終了要求ではありません。無限ループや入力待ちの子は自動では止まりません。
親は終了メッセージや close で子を終了させてから join します。
子が結果を送る間は親が結果を受信し、満杯の結果 Channel を残して join しないようにします。
スコープの逆順解放だけでは通信プロトコルのデッドロックは防げません。
特に複数ワーカーの起動途中で失敗した場合も、既に起動したワーカーの入力を close
してから Thread ハンドルのスコープを抜けます。

強制停止と例外の巻き戻しは導入しません。子の `panic^`・境界違反・スタック超過は
現在と同じくプロセスを終了し、他スレッドの dispose は保証しません。
回復したい失敗はワーカーの通常の結果として Channel に流します。
すべての Thread ハンドルの後始末を済ませてから main のシャードとプロセス資源を解放します。

## 典型的な使い方

ワーカープールは次の順序で構成します。以下はアルゴリズムであり R^ のコードではありません。

1. `Channel<Job>` と `Channel<Result>` を容量付きで作る。
2. 両 Channel を起動引数に含めて N 本のワーカーを spawn する。
3. ワーカーは Job を受信し、計算して Result を送る。Job の終端で終了する。
4. 親は仕事の投入と結果の回収を並行に進める。必要なら投入専用スレッドを設ける。
5. 最後の送信者が jobs を close する。ワーカーは残りを処理する。
6. 親は期待数の結果を回収して全ワーカーを join する。その後 results を close する。

同じ型の独立したプールは別の Channel を作るだけです。
二つの段階をつなぐパイプラインでは、各段階へ異なる Channel インスタンスを渡します。
受信値の所有配列は周ごとのスコープで回収し、常駐ワーカーのスタックを際限なく伸ばしません。

## 実装順序と完了条件

### 1. 実行コンテキストの分離

- `runtime/rhat_runtime.c` のスタック管理・VEH・コールバック状態を分離する。
- `src/llvm.c` のスタック取得・入口・終了コードを変更する。
- 単一スレッド、所有配列の返却、C コールバック、モジュールキャッシュを回帰確認する。
- ランタイム ABI とキャッシュ識別子を更新し、新旧オブジェクトの混在を防ぐ。

### 2. 起動境界の検査と固定サイズ転送

- 起動入口の登録、到達先の束縛・実行状態の依存検査、転送可能型の検査を加える。
- 起動を通常の呼び出しグラフと区別してスタック配置を計算する。
- `runtime/rhat_thread.c` と OS 移植層を追加し、spawn / join / 自動 join を実装する。
- 同じ入口を複数同時起動してもローカル状態・スタックが混ざらないことを確認する。

### 3. Channel の共有本体と固定サイズ通信

- `runtime/rhat_channel.c`、`std.channel` の公開型、コンパイラの専用操作を追加する。
- 容量、close、FIFO、複数送受信者、clone、Disposable、起動引数の保持を実装する。
- 型が同じ独立した Channel と、起動時に選ぶパイプラインを確認する。

### 4. 所有配列と実用ワーカープール

- 可変サイズの内部形式、送信の容量予約、受信先への直接構築を実装する。
- 送信元の配列の変更・破棄・送信者終了後もメッセージが独立していることを確認する。
- 大きなメッセージ、失敗時の予約返却、長時間の周回でメモリが増え続けないことを確認する。
- `examples/` に固定サイズの仕事と所有バイト配列の結果を返す例を追加する。

### 5. 移植性・競合・性能の確認

- Windows と POSIX の起動・終了・条件変数・待機の再確認ループを検証する。
- LSP の `lsp/port/thread.*` は既存の OS 抽象として参考にし、ランタイムから
  LSP サーバー本体への依存は作らない。共通化する場合は独立した移植層へ移す。
- close と send / receive の競合、満杯・空の待機、最終保持の解放、OS 起動失敗を検証する。
- 拒否ケースとして参照・スライス・文字列ビュー・通常の Disposable・親の束縛への
  間接アクセス・Channel を含むメッセージ・Thread の転送を確認する。
- C のランタイム部分を競合検査ツールで確認する。生成 LLVM を計測していない検査では
  R^ 本体までデータ競合を検査したと扱わず、必要なら生成コードにも計測を入れる。
- 単一スレッドの配列ベンチ、スレッド起動時間、Channel のスループット・待機時 CPU・
  実メモリと仮想予約量を測る。マイクロベンチだけで性能を判断しない。

「別シャードで安全に実行できる」「親の参照を持ち込めない」「同じ型の経路を分離できる」
「送信者の寿命からメッセージが独立する」「正常終了時に保持と OS 資源が残らない」を
最初の実用版の完了条件とします。
