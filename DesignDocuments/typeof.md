# typeof^ と型の綴り（signature^）

`typeof^ 式` は式の静的な型を表す型式です。`型.signature^` はその型の正規の綴りを文字列で返します。

```rhat
let^ write = p^ x { print^(typeof^(x).signature^, x) }
write(1)        # i32^ 1
write("s")      # string^ s
write(true^)    # bool^ true
```

型を書かない引数は呼び出しの形ごとに具体化されます（[設計](design.md)）。
`typeof^(x)` はその具体化での `x` の型を指し、`signature^` は具体化ごとに異なる文字列定数になります。

## 実装状況

- 段階1（実装済み）: `typeof^` の構文、`.signature^`、エディタでの被演算子の参照。
- 段階2（実装済み）: 関数本体の注釈と `fits^` の右辺に書く `typeof^`、型の厳密一致 `typeof^(a) = typeof^(b)`。
- 段階3（実装済み）: `let^ t = typeof^(x)` による関数内の型の別名と、`for^ typeof^(x):` の型での振り分け。
- `typeof^` は引数・返り値・フィールドの注釈には書けません。これらの位置では、宣言から決まる `関数.ReturnType^`（実装済み）を使います。
- 第三段（見送り）: `typeof^(x).ZERO`、`typeof^(x){...}` による構築など、型のメンバの参照。

## 構文

`typeof^(式)` は括弧の中を被演算子にします。`typeof^(x).signature^` は `x` の型の綴りです。
括弧なしの `typeof^ 式` は `try^` と同じ優先順位の前置演算子で、呼び出しとメンバアクセスを被演算子に含み、
二項演算は含みません。`typeof^ p.n` は `p.n` の型です。L^ の `typeof^` と同じ規則です。

## typeof^ は型を返す

L^ の `typeof^` は型記述子という値を返します（`type^<T>`）。R^ は具体化ごとに単相化するため、
具体化の中では式の型が常に一つに決まり、実行時の記述子を持つ必要がありません。
R^ の `typeof^` は型そのものを表します。

- 答えは検査器がその式に決めた**静的な型**です。合併型は合併型のまま、`ref^ dyn^ D` もそのまま答えます。
  いま入っている選択肢を問うのは `fits^` の役割です（[fits.md](fits.md)）。
- 被演算子は**評価しません**。副作用は起きず、移動・借用・キャプチャの対象にもなりません。
  `typeof^(side())` は `side` を呼びません。ただし推論のために、呼び先の具体化は作られます。
- 値の位置に単独で書くことはできません。`print^(typeof^(x))` はエラーです。

## 型の位置

関数本体の中の注釈（`let^`・`var^`・分解束縛）と、`fits^` の右辺に書けます。
配列・参照・合併などの型の部品にもなります。

```rhat
let^ copy = p^ x {
    var^ y:typeof^(x) = x
    let^ pair:typeof^(x)[2] = {x, x}
    var^ maybe:typeof^(x) | nil^ = nil^
}
```

引数・返り値・フィールドの注釈には書けません。これらの型は本体より先に、
具体化の文脈なしに解決されるためです。`f^ a, b:typeof^(a)` で「`b` は `a` と同じ型」を表す用途は、
呼び出しの照合と多重定義の選択に具体化ごとの型を持ち込む必要があり、今回は扱いません。
返り値は本体から推論されるので、注釈を省略できます。

`let^ t = typeof^(x)` で型に名前を付けられます（[型の別名](generics.md#関数内の型の別名)）。
`t` が表す型は、**束縛した位置**で具体化ごとに確定します。C++ の `using T = decltype(x)` と同じです。
その後で `x` が絞り込まれても、同じ名前の変数で隠されても、`t` の型は変わりません。

```rhat
var^ x:i32^ | nil^ = 3
let^ t = typeof^ x
if^ x? {
    print^(typeof^(x) = i32^)    # true: ここでの x は i32^
    print^(t = i32^)             # false: t は i32^ | nil^ のまま
}
```

## 型の厳密一致

`typeof^(a) = typeof^(b)`・`!=` は、二つの型が同一かを具体化ごとにコンパイル時に決めます。
片側には型の名前も書けます（`typeof^(x) = string^`、`typeof^(x) = T`）。
`fits^` が適合（派生・合併の選択肢を含む）を問うのに対し、こちらは同一性だけを問います。
`i32^` は `i32^ | nil^` に適合しますが、同一ではありません。

```rhat
let^ show = p^ x {
    if^ typeof^(x) = string^ {
        print^("text", x.bytes.len)
    el^ typeof^(x) = A:
        print^("A", x.a)
    else^:
        print^("other", x + 1)
    }
}
```

結果は静的に決まるので、静的な `fits^` と同じく、到達しない分岐を具体化・検査しません。
上の例で `show(1)` は `x.bytes` を検査しません。
本体からの型の要求の収集では、比較より後の要求は条件付きとして扱います（`fits^` と同じ）。

### 型での振り分け

`for^` の主題に型を書くと、各腕を型の厳密一致で判定します。`for^` は主題を `let^` に束縛して `=` で比べる形に
展開されるので、関数内の型の別名がそのまま働きます。専用の処理はありません。到達しない腕は検査されません。

```rhat
let^ of = template^ f^ x -> string^ {
    for^ typeof^(x):
    when^ string^: x
    when^ i32^, i64^: "int"
    other^: x.name();
}
```

`for^ x:` と `when^ fits^ T:` の組み合わせとは判定が異なります。

- `for^ typeof^(x):` は静的な型の完全一致です。`x` が合併型なら、どの選択肢の腕にも入りません。派生型も基底の腕に入りません。
- `for^ x:` と `when^ fits^ T:` は適合判定です。合併型なら実行時にタグで振り分け、派生型は基底の腕に入ります。

式の形では `other^:` が必須です。型の主題には、腕で尽くすべき選択肢の集合がないためです。
`it^` はその型の別名になります。

### 呼び出し側に型を任せた関数

`let^write = p^x {...}` の `write` そのものには一つの型がありません。
答えをプログラム全体の呼び出し方に依存させないため、`typeof^(write)` はエラーにします。
引数の型がすべて決まった関数や、すべて型付きの多重定義は型を持ちます。
多重定義は交差型 `f^i32^ -> i32^; & f^string^-> i32^;` になります。

エディタのホバーは観測として、解析で得た具体化の一覧を交差の形で表示します（[lsp.md](lsp.md)）。

## signature^

`型.signature^` は型の正規の綴りを `string^` のコンパイル時定数として返します。
型の式であればどこにでも付けられます。

```rhat
typeof^(x).signature^      # 具体化での x の型
Float2.signature^          # 別名を展開した "Vec2<f32^>"
T.signature^               # def^ の型パラメータ。具体化した型の綴り
Self^.signature^           # 宣言元の型
i32^.signature^            # "i32^"
```

- 型の別名は展開し、公称型は名前で書きます（`Vec2<f32^>`、`Mode`）。
- 関数型・交差型・合併型・参照・配列は型注釈と同じ文法で書くので、そのまま注釈として読み戻せます。
- 別モジュールの型は `std.text.Builder` のようにモジュールの完全な名前で書きます。
  インポートの別名はモジュールごとに異なるため、この綴りは書いたモジュールで読み戻せるとは限りません。
- 値に直接付けた `x.signature^` はエラーです。`typeof^(x).signature^` と書きます。

### ハット付きにする理由

L^ は `typeof^(x).signature` とハットなしで書きます。記述子を普通のテーブルとして読ませるためです。
R^ の `typeof^` は型そのものを返すので、`signature` は型の名前空間（型定数・静的メンバ・`enum^` の選択肢）
に入ります。ハットなしにすると、利用者が `signature` という名前の型定数や選択肢を作れなくなります。
ハット付きの名前は利用者が宣言できないため、`signature^` は何も予約せずに衝突を避けられます。
言語が定義する名前にハットを付ける、という R^ と L^ に共通する原則にも合います。

## 関数の返り値型（ReturnType^）

`関数.ReturnType^` は、その関数を呼んだときに返る型を表す型式です。
関数の宣言を変えれば自動で追従するので、推論に任せた返り値型を、フィールドや公開する署名に手書きせずに書けます。

```rhat
let^parse = p^text:string^ { ... }              # return type inferred from the body

def^Entry {
    self^{ value:parse.ReturnType^ }             # field annotation
}
let^make = p^ -> parse.ReturnType^ { ... }      # return annotation
var^tasks:overload^serve(ref^TcpConn).ReturnType^[grow^] = {}
```

- `typeof^` と違い、具体化の文脈なしに宣言から決まります。したがって引数・返り値・フィールド・トップレベルの注釈を含め、
  型を書けるすべての位置に書けます。関数本体の中で式の型が欲しいときは、従来どおり `typeof^` を使います。
- 左辺は一つの候補に決まる関数でなければなりません。候補が一つの名前、名前付きの候補（[overloads.md](overloads.md#名前付き関数を候補にする)）、
  `overload^` の結果のいずれかです。多重定義の名前に直接付けるとエラーです（TypeScript の `ReturnType<typeof f>` が最後の候補を黙って選ぶ問題を避けます）。
  メソッドは `Type.method.ReturnType^` と書きます。
- 型を書かない引数を持つ関数は、具体化ごとに返り値型が変わるので直接は使えません。`overload^f(i32^).ReturnType^` のように型を与えます。
- 返り値のない関数に付けるとエラーです。
- 返り値型の推論が本体の検査を必要とする場合、その関数を先に推論します。
  「構造体のフィールドが `f.ReturnType^` で、`f` がその構造体を返す」のような循環はエラーです（`def^` の合成の循環として報告されます）。
- yieldable な関数（[coroutines.md](coroutines.md)）の `ReturnType^` は、その関数のフレーム型です。
  コルーチン専用の名前は設けません。フレームの大きさは本体を下ろして決まるので、フィールドや配列の要素に置くと、
  その時点でコルーチンを下ろします。

L^ の `ARG0.ReturnType`（呼び出しが答える型）に対応します。R^ では言語が定義する名前にハットを付けるので、`ReturnType^` と書きます。

## 実装

- 構文木では、`typeof^` を `E_TYPE` の式として表します。型の指定（`Spec`）には新しい種類
  `SPEC_TYPEOF` を使い、被演算子の式を `operand` に持ちます。
  `def^` の型パラメータを具体化するときの複製は、被演算子も複製します。
- 名前解決では、被演算子を周囲の式と同じローカル名の範囲で解決します。
  `型.signature^` は名前解決の段階で型の式 `E_TYPE` に正規化します。
- 推論では `.signature^` を `string^` とし、被演算子は推論しません。被演算子は本体からの型の要求にも参加しません。
- 生成時に、その具体化での被演算子の型を推論し、`type_name` の綴りを文字列定数として出力します。
  被演算子のコードは生成しません。
- エディタ向けには、被演算子に現れるローカル名の参照を記録します。
- `関数.ReturnType^` と `overload^f(型…).ReturnType^` は型の指定の種類 `SPEC_RETURN` です（`overload^` の形は `count` が 1、
  引数の型を `params` に持ちます）。名前解決では関数名を正規化し、`型.メソッド` なら型の名前だけを解決します。
  型にするときは候補を選び（`overload^` の形は通常の呼び出しと同じ `overload_select`）、その引数型の具体化を作って
  返り値を推論します。推論中の具体化から再び推論に入ることがあるため、推論中の具体化は内側の推論では飛ばします。
- 型の指定は具体化の間で共有され、解決結果をキャッシュします。`typeof^` を含む指定は、
  具体化ごとに複製を作り、`typeof^` の部分にその具体化での型を入れてから解決します。
  元の指定にはキャッシュを残しません。文脈なしに解決しようとした場合（引数の注釈など）はエラーにします。
- 型の比較は名前解決で両辺を型の式にそろえます。結果は `fits^` と同じ分岐の事実として記録し、
  到達しない分岐を除きます。

## 現時点の制限

- 内側の関数から、外側の関数のローカルを `typeof^` だけで参照することはできません。
  被演算子はキャプチャを起こさないため、内側の関数からはその名前が見えません。
- 引数・返り値・フィールドの注釈には書けません（「型の位置」参照）。
- `overload^id(f64^).ReturnType^` で型を与えても、型を書かない引数の関数がどこからも呼ばれないと、
  従来どおり「call shape がない」エラーになります（`ReturnType^` は推論だけで、本体を下ろさないため）。
- 型のメンバ（`typeof^(x).ZERO`）・構築（`typeof^(x){...}`）・静的メンバの呼び出しは未対応です（第三段、見送り）。
  型のメンバは名前解決の段階で解決していますが、`typeof^` の型は検査の段階まで決まりません。
  Zig の `@TypeOf(x)` や C++ の `decltype(x)` には前例があり、関数に名前付きの型パラメータがない R^ でも
  需要が出る可能性があります。
