# rhatls — R^ 言語サーバー

`rhatls` は C11 で実装した stdio 接続の Language Server Protocol サーバーです。
L^ の通信、JSON-RPC、URI、UTF-16 座標変換、スレッドの実装を移植し、
解析部分は R^ の構文解析・名前解決・型検査・寿命検査・データスタック検査へ接続しています。
L^ の VM、ホスト設定、LTON、可視化専用 RPC と DAP は組み込みません。

## 起動とインストール

通常のビルドで `rhat` と一緒に生成します。

```powershell
cmake -S . -B build
cmake --build build --config Debug
.\build\Debug\rhatls.exe --stdio
```

エディターの LSP クライアントから、この実行ファイルを子プロセスとして起動してください。
標準入力・標準出力は Content-Length 付き JSON-RPC 専用です。
VS Code では言語クライアント拡張から接続する必要があります。
LSP クライアントそのものは、このリポジトリには含めません。

```powershell
cmake --install build --config Release --prefix C:/tools/rhat
C:/tools/rhat/bin/rhatls.exe --stdio
```

インストール先の `share/rhat/stdlib` を優先し、開発時には同梱ソースの `stdlib` を使います。
`--stdlib DIR` で探索先を指定できます。`DIR/std/random.rh` が存在する配置を指定します。
`--version`、`--help` にも対応します。
`-DRHAT_BUILD_LSP=OFF` を指定すると、コンパイラのみをビルドします。
外部の L^ チェックアウトや、ビルド時のネットワーク取得は不要です。

## 対応機能

- 構文・型・公開制御・参照寿命・所有領域について、コンパイラと同じ診断。
- ローカル変数、引数、フィールド、構造体型、関数・メソッドのホバーと定義移動。
- 解析済みの参照検索、文書内ハイライト、文書シンボル、ワークスペースシンボル。
- 名前、組み込み型、言語構文、名前空間、構造体メンバ、配列メンバの補完。
- 継承と非公開メンバを考慮したメンバ補完。
- 関数・メソッドのシグネチャヘルプ。関数の別名では交差の各署名を表示。
- 引数型で選択したオーバーロードと、利用者定義演算子の定義移動。
- 解決済みの型、関数、引数、変数、フィールドなどの semantic tokens。
  インポートしたモジュールのパス各部と別名は、宣言・使用箇所とも `namespace` として色付けします。
  コメント・文字列・数値・キーワード・演算子は TextMate 文法に任せ、`^` の薄い配色も上書きしません。
- UTF-16 座標による差分編集と全文置換。日本語・補助平面文字・CRLF に対応。
- 未保存の文書と未保存の依存モジュールの解析。文書バージョンの逆行を拒否。
- 保存・外部ファイル変更通知による再検査、診断の消去、リクエストのキャンセル。

`initialize` の `workspaceFolders`、または従来の `rootUri` をモジュール探索に使います。
追加の探索先は `initializationOptions` で指定します。

```json
{
  "modulePaths": ["C:/work/project/modules"]
}
```

パスは絶対パスで渡してください。標準モジュールは、コンパイラと同じく専用の標準ライブラリから探索します。
独立して開いた `module^` ファイルも、ライブラリの宣言として検査します。
そのため、公開定数を含むライブラリを編集するために、仮のエントリーファイルを作る必要はありません。

## コンパイラとの接続

フロントエンドに `tooling` オプションと、検査済みの名前解決記録を追加しています。
メンバは実際に選ばれたフィールド・メソッドへ、公称型は宣言元へ、ローカル名は選択された束縛へ結び付けます。
同名の別モジュール・別スコープを、文字列の一致だけで同一視しません。
型が決まっている箇所では、通常の型推論とナローイングの結果を表示します。
通常のコンパイルでは、これらの記録とソース保持を行いません。

`CompilerHooks` は検査用の割り当て境界と診断境界です。
検査中の確保を一回の解析単位で回収し、言語の診断は `setjmp` / `longjmp` の境界へ戻します。
CLI ではフックを設定しないため、従来どおり診断を表示して終了します。
LSP ではエラー後もプロセスを維持し、次の編集を検査します。
ディスクのソースを書き換えず、オーバーレイをモジュール探索と読み込みへ渡します。

受信スレッドは編集・キュー・初期化・終了処理を担当し、検査は一つのワーカースレッドに限定しています。
待機中の再検査は合流し、古いバージョンの解析結果は公開しません。
同じ編集状態での問い合わせには解析済みのインデックスを再利用します。
文書を閉じると、その未保存バッファを外し、残る文書を再検査します。

## 現時点の範囲

解析対象は開いている文書と、その静的な import 依存です。
参照検索とワークスペースシンボルも、この解析済みの範囲を対象にします。
未使用のテンプレートなど、コンパイラが本体を具体化していない部分の型情報は限定的です。
同じ構文位置に複数の具体化が対応する場合、ホバー・定義移動では最初に得た解決結果を使います。
構文エラーで構文木を作れない場合には、取得できた宣言までを表示します。
メンバ補完では編集中の `receiver.` を補修して検査する経路も用意しています。
診断は CLI と同じく、一つの検査対象で最初のエラーを表示します。

名前変更・整形・コードアクションは、未対応の機能として capability を通知しません。
特に、具体化していない本体まで完全に追えていない状態で、一部の参照だけを書き換える rename は提供しません。

## デバッグについて

R^ 専用の DAP サーバーは作りません。
ネイティブ実行ファイルには、GDB・LLDB・Windows デバッガと、それらの既存のアダプターを利用できます。
VS Code のデバッガ UI 自体は DAP を使うため、「DAP を使わない」ではなく、
「R^ 独自の DAP サーバーを実装しない」という分担です。

ただし、現在の LLVM IR には R^ のソース位置・変数型を表すデバッグ情報を出力していません。
R^ ソース上のブレークポイントや変数表示を実現するには、別途 LLVM のデバッグ情報を生成する必要があります。
LSP の位置・型情報を追加しただけでは、実行ファイルにその情報は入りません。

## 検証

`tests/lsp.py` は実際の `rhatls` と Content-Length 付き stdio メッセージを交換します。
未保存バッファ、依存変更、構文・意味エラーからの復帰、UTF-16、名前解決、補完、
公開制御、連続編集、初期化・終了を検証します。CTest の `lsp` として登録しています。
