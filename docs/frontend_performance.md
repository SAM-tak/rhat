# フロントエンドの検査時間

`rhat check` は読込み・構文解析・モジュール解決・型推論・寿命検査・
データスタック計画までを実行する。検査結果をディスクに保存して
次回の検査を省く方式は使わない。変更されたソースも毎回検査する。
配列伸長と範囲ループのコード生成向け最適化は、コード生成や `--dump-ir` を
指定したときに実行する。通常の `check` では診断を行わない最適化処理を省く。

## 重複処理の除去

- 構文解析の型構築判定は、字句解析後に集めた `def^`・`struct^`・
  `errordef^` の名前を参照する。式ごとに全トークンを走査しない。
- 文字列・引用識別子・補間文字列の復号は、一つの作業バッファを共用する。
  保存するトークンには実際の文字数だけをコピーする。文字列ごとに
  ソースの残り全部の長さのバッファを割り当てない。
- 戻り値推論が固定点に達した具体化群の長さを `Program` に保存する。
  次回はその後に追加された具体化群だけを収束させる。固定点までに必要な
  呼出し先も登録済みであり、既存具体化の引数型・依存関係は変わらない。
  新しい型による具体化と、その再帰呼出しは引き続き検査する。
- 組込み型は種類で直接参照し、参照型・配列型などは要素型ごとに検索する。
  型指定の解決結果と、関数ごとの具体化一覧も再利用する。
- トップレベル変数を参照する関数の検査では、関数名の値参照と直接呼出しを
  一度だけ分類する。

## 数値とメモリ

狭い浮動小数点型のリテラルは、まず `strtod` の近似値で表現可能値の候補を
探す。その後、元の十進数との厳密比較で候補を補正し、中点との厳密比較で
最近接偶数丸めを決定する。探索の各段階で160桁の十進数へ変換する必要がなくなる。
近似値をそのまま採用しないため、中点のすぐ上下にある長いリテラルも区別する。

CLI の `mem` はゼロ初期化済みの領域を64 KiB以上の単位で確保する。
領域の寿命はプロセス終了までとし、個別解放はしない。伸長する `List` の
バッファは従来どおり `realloc` を使う。LSP は既存の `CompilerHooks` による
セッション単位の確保・解放を使い、CLI の領域を共有しない。
推論の変数スナップショットは一括確保し、スタック計画の作業領域は命令間で再利用する。

## 再計測

```powershell
python bench/check_frontend.py --compiler build/Release/rhat.exe `
  --source ../rhat-gfx/samples/mini_doom.rh --module-path ../rhat-gfx `
  --samples 20 --output build/mini_doom-check.json
```

`--baseline` に旧コンパイラを指定すると、同じ入力を交互に計測する。
ウォームアップを各2回行い、起動・終了を含む壁時計時間の全サンプル、中央値、
最小値・最大値、入力とコンパイラのハッシュを保存する。終了コードが0でない
検査や、計測中にソース・コンパイラが変わった場合は結果として採用しない。

2026-11-01 の Windows Release ビルドで、実際の `mini_doom.rh` を20回比較した結果は、
旧版の中央値3.306秒に対し、変更後は0.082秒（最小0.074秒、最大0.176秒）。
型・寿命・スタック検査を含む成功した検査の比較であり、単発時間にはOS負荷の変動が含まれる。
